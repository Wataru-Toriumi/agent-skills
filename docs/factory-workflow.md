# 要求から実装・検証・PRへ

[implement-work-item](../plugins/forge/skills/implement-work-item/SKILL.md) を選ぶと、
一件の作業項目について実装・検証・提出の進行状態を記録する。
既存スキルは単独でも使え、この手順や他のプラグインの導入を必須にしない。

## 工程間で渡す情報

| 項目 | 内容 |
| --- | --- |
| 入力 | 作業ID、要求ID、設計資料、リポジトリ、開始SHA |
| 範囲 | 変更可能箇所、許可操作、対象外、依頼の到達点 |
| 合格条件 | 受け入れ条件、検証コマンド、必要なレビュー |
| 状態 | 未着手・実行中・判断待ち・検証失敗・完了 |
| 証跡 | 対象SHA、未コミットなら差分の識別情報、実行結果・ログ、レビュー結果 |
| 再開条件 | 未解決事項、次の工程、再試行回数・上限、判断事項と担当 |
| 運用改善の場合 | 元の障害・改善策の根拠と採否、効果指標・比較元・観測期間・見直しの条件、適用と効果確認の状況 |

要求と条件をinkから受け取り、必要に応じてprobeで検証方法を整理する。
forgeで実装・検証・レビューし、依頼に応じてコミット・PRへ進む。
記録の書式は [作業記録のひな形](../plugins/forge/skills/implement-work-item/assets/work-record.md) を参照する。
保存先の指定がなければ会話内で扱う。

## 運用改善から始める

pulse の `write-postmortem` または `improve-operations` から、問題の根拠と採用する改善策を受け取る。
要求が曖昧なら ink の `clarify-requirements`、作業の範囲や受け入れ条件の整理が必要なら `write-work-item` を使う。
条件が揃い、実装も依頼されていれば forge の `implement-work-item` へ直接進める。毎回すべての工程や文書作成を必須にしない。

原因の仮説、対策の採否、未決事項を保持し、調査が必要な作業と実装できる作業を分ける。
引き継ぎの詳細は [pulse の手順](../plugins/pulse/skills/improve-operations/references/implementation-handoff.md) を参照する。

たとえば重複したイベントで同じ通知が二度届く問題なら、対象のイベント・受信者を絞り、
同じイベントの再送では通知が増えず、別のイベントは通知されることを実装の受け入れ条件にする。
適用後の重複通知数と通知漏れは運用で評価し、比較元・計測方法・観測期間・目標は既存の根拠や合意から決める。
原因が未確定なら、この対策で解消すると断定せず、必要な調査と分ける。

forge は対象の版・差分・検証結果・適用状況を元の改善策に対応付けて返す。
効果評価も依頼され、適用後の観測データが揃えば pulse の `improve-operations` で評価する。
未適用や観測不足なら、次に必要なデータ・時期・担当を残し、実装済みと効果確認済みを混同しない。

## 要求・設計から検証を具体化する

要求・設計の検証を具体化するときは、ink から probe へ対象の版・受け入れ条件・設計リスクと既存の検証計画を渡す。
必要な方針・ケース・レビュー・形式検証だけを選び、戻った内容を元の要求へ対応付ける。計画と実行結果を分け、合否を左右する未決事項は ink へ戻す。

## 完了と再開の例

「申請者以外が申請内容を閲覧できないこと」が受け入れ条件なら、正常な閲覧と権限拒否を検証し、
対象SHA・結果・レビューを記録する。PR作成だけでは完了にならない。
CIが失敗した場合は検証失敗として次の修正へ引き継ぐ。

再開時にheadが変わっていたら、記録との差分を確認する。権限判定を修正したなら、
そのテストとレビューを更新する。検証した内容を変更せずコミットした場合は、内容一致を確認して証跡を新しいSHAに対応づける。
判断や権限が足りなければ判断待ちにし、無関係な工程まで繰り返さない。
