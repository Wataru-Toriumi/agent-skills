# 障害に対応する

利用者への影響を減らす。原因の確定を待たず、根拠のある軽減策と調査を進める。
入力が対応記録だけなら、その範囲の分析と次の確認を返す。

## 状況を揃える

- 発生・検知時刻とタイムゾーン、対象環境、失敗する操作、影響範囲、継続状況を確認する。重大度は既存基準に従い、不明なら影響から暫定評価する。
- 現在の担当・対応中の操作・連絡経路を把握する。複数人なら指揮・作業・状況共有の役割を整理し、同じ対象への競合操作を防ぐ。
- 影響度と既存の対応基準から、調査の再評価時点とエスカレーション先を決める。基準がなければ提案し、調査の停滞・必要な権限の不足・影響拡大を引き継ぎ条件にする。影響拡大時は再評価時点を待たない。
- ログ・指標・変更履歴を時刻と出典付きで残す。観測した事実、仮説、未確認事項を分け、デプロイ直後という理由だけで原因を断定しない。

## 切り分けと軽減を進める

1. **次の確認を選ぶ:** 仮説を支持・否定できる観測を、影響と調査負荷で優先する。対象・時間範囲を絞り、機密情報を共有記録へ転記しない。
2. **軽減策を比較する:** 既存ランブックと現状を照合し、期待効果・影響範囲・適用条件・戻し方を示す。再試行の負荷増加や、データ変更後のロールバック互換性を確認する。
3. **範囲内で実行する:** 依頼・権限の範囲で進める。本番を変える直前に対象・手順・中止条件と既存の許可を照合し、不足する許可だけ確認する。調査の依頼から再起動・切り戻し・データ修正へ広げない。
4. **結果を測る:** 調査・操作の時刻と観測結果を記録し、再評価時点と引き継ぎ条件を確認する。期待した改善がない、前提が崩れた場合は同じ操作を繰り返さず、中止・切り戻し・担当への引き継ぎを選ぶ。

手順の粒度は [対応記録の例](references/incident-example.md) を参照する。
調査や操作ができない場合は、その制約と担当者が次に確認する項目を示す。実行していない操作を実施済みとして記録しない。

## 復旧を確認して引き継ぐ

- アラートの消失に加え、影響した利用経路、滞留処理、データの不整合を確認する。観測期間と結果を示し、影響の軽減・復旧・原因解消を区別する。
- 現在の影響、実施済み操作と効果、残る仮説、次の担当・確認時点を短くまとめる。不明な担当や時刻は未定とする。状況共有は依頼された宛先・範囲で行う。
- 事後の振り返りも依頼されたら、対応記録を [write-postmortem](../write-postmortem/SKILL.md) に渡す。
