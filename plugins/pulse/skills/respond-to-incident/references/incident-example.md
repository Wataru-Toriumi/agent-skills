# 対応記録の例

架空の予約 API 障害。時刻は JST。

| 時刻 | 観測・操作 | 分かること |
| --- | --- | --- |
| 10:02 | API の新バージョンを展開 | 変更履歴。原因かは未確認 |
| 10:05 | 予約 API の 5xx が増加 | 利用者への影響あり。対象地域は調査中 |
| 10:07 | DB 接続待ちが増加 | 接続不足の仮説を支持。増加の起点は未確認 |

## 次の判断

- **確認:** バージョン別・地域別の失敗率、接続数、直近の設定変更を照合する。
- **引き継ぎ:** 再評価時点でも切り分けが進まない、または DB の調査権限がない場合は、調査済みの範囲と残る仮説を添えて担当へ引き継ぐ。影響が広がれば前倒しする。
- **軽減候補:** 旧版への切り戻し。DB スキーマの互換性と進行中処理への影響を確認し、許可された対象だけを操作する。
- **中止条件:** 切り戻し後に失敗率が増す、互換性エラーが出る場合。実行前に再展開や担当への引き継ぎを含めた対応を決める。
- **復旧確認:** 予約の受付と確定、滞留の解消、重複予約の有無を観測する。判定期間は通常の変動と処理時間から選ぶ。

これらは候補であり、切り戻しや復旧が完了した記録ではない。
基礎となる役割分担と対応記録の考え方は [Incident Response](https://sre.google/workbook/incident-response/) を参照する。
