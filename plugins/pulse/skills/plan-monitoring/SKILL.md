# 監視と通知を設計する

利用者の失敗を検知し、対応につながる監視を選ぶ。既存の監視基盤と運用体制を優先する。

## 守る利用経路を決める

- 要求、構成、既存の指標・通知・障害記録から、重要な利用経路と失敗時の影響を拾う。API の応答だけでなく、非同期処理の完了やデータの正しさも対象に応じて確認する。
- 信頼性を測る指標（SLI）、目標と評価期間（SLO）、対応時間帯を確認する。未合意の目標・閾値は提案として扱い、必要な計測や合意を残す。
- 利用者から見た成功・遅延と、原因を調べる内部指標を分ける。遅延・トラフィック・エラー・飽和を出発点に、今回の経路に必要なものを選ぶ。

## 検知から対応までをつなぐ

1. **測る:** 指標の取得元、対象・除外条件、集計方法と窓を定める。比率なら分子・分母を示す。要求ゼロ・計測欠損・処理停止を区別し、低トラフィック時の判定も決める。
2. **通知する:** 利用者への影響と対応までの猶予から、即時呼び出し・営業時間内の対応・観察を分ける。SLO があればエラーバジェットの消費速度も使い、未定なら閾値を決めるための根拠を示す。
3. **動けるようにする:** 対応先、最初に見る情報、軽減策の適用条件、エスカレーション先、復旧の判断を通知と結び付ける。重複通知の集約や抑止には解除条件を置く。
4. **確かめる:** 過去の障害や模擬データで、発火・通知到達・復旧・欠損時の挙動を確認する。誤検知、見逃し、検知時間を評価し、実施していなければ検証計画として残す。

具体化には [監視の判断例](references/monitoring.md) を使う。設定・クエリも依頼されたら、実在する指標名と利用製品の仕様を確認して作る。

## 結果を返す

監視対象ごとに「利用者への影響／指標と判定条件／通知先と初動／検証方法」をまとめ、未決事項と検知できない範囲を添える。
小さな見直しは変更する条件と理由だけでよい。既定の出力先は会話。設計の依頼だけで監視設定を適用したり、試験通知を送ったりしない。
