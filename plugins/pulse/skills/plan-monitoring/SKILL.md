# 監視と通知を設計する

利用者の操作や処理が失敗したときに検知でき、担当者が対応に移れる監視を選ぶ。既存の監視基盤と運用体制を優先する。

## 守る利用経路を決める

- 要求、構成、既存の指標・通知・障害記録から、重要な利用経路と失敗時の影響を拾う。API の応答だけでなく、非同期処理の完了やデータの正しさも対象に応じて確認する。
- ink・forge からの依頼では、設計の版・対象SHAや差分、変更前後の経路、対象環境、実装・適用状況を照合する。既存の監視案を再利用し、今回変わる挙動と計測だけを見直す。
- 信頼性を測る指標（SLI）、目標と評価期間（SLO）、対応時間帯を確認する。未合意の目標・閾値は提案として扱い、必要な計測や合意を残す。
- 利用者から見た成功・遅延と、原因を調べる内部指標を分ける。遅延・トラフィック・エラー・飽和を出発点に、今回の経路に必要なものを選ぶ。

## 検知から対応までをつなぐ

1. **測る:** 指標をどこから取得し、何を集計に含め、何を除くかを決める。集計方法と、どの時間範囲を集計するかも定める。比率なら分子・分母を示す。要求ゼロ・計測欠損・処理停止を区別し、低トラフィック時の判定も決める。
2. **通知する:** 利用者への影響と対応までの猶予から、即時呼び出し・営業時間内の対応・観察を分ける。SLO があればエラーバジェットの消費速度も使い、未定なら閾値を決めるための根拠を示す。
3. **動けるようにする:** 対応先、最初に見る情報、軽減策の適用条件、エスカレーション先、復旧の判断を通知と結び付ける。重複通知の集約や抑止には解除条件を置く。
4. **確かめる:** 過去の障害や模擬データで、発火・通知到達・復旧・欠損時の挙動を確認する。誤検知、見逃し、検知時間を評価し、実施していなければ検証計画として残す。

具体化には [監視の判断例](references/monitoring.md) を使う。設定・クエリも依頼されたら、実在する指標名と利用製品の仕様を確認して作る。

新旧版が共存する場合は、各経路の指標と判定条件を対応付け、切替中の二重計上・計測欠損・通知抑止の影響を確認する。
旧監視の撤去条件は、新しい監視の適用・検証状況と旧経路の利用状況から決める。新しい設計や PR ができた段階で、旧監視を撤去した、または撤去できるとは判断しない。

## 結果を返す

説明の推敲・図解が必要な場合や、発表資料・HTML の説明ページを求められた場合は、[sketch との連携](../write-postmortem/references/sketch-collaboration.md)に従い、利用可能なスキルで整えて元の内容と照合する。

監視対象ごとに「利用者への影響／指標と判定条件／通知先と初動／検証方法」をまとめ、未決事項と検知できない範囲を添える。
小さな見直しは変更する条件と理由だけでよい。既定の出力先は会話。設計の依頼だけで監視設定を適用したり、試験通知を送ったりしない。

ink・forge には、対象の版・環境、採用済みの条件と提案・未決事項、必要な計測・設定・初動の変更、検証方法を返す。
監視の設計・設定作成・適用・発火や通知到達の検証を分け、実施した範囲だけを報告する。存在しない指標や未合意の閾値・担当を、設定可能な確定事項として補わない。
