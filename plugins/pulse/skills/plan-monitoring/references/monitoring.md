# 監視の判断例

## 非同期処理の完了を測る

予約サービスなら、受付 API の成功率に加え、受け付けた予約が期限内に確定する割合を見る。
HTTP 200 だけでは、キューに滞留した予約の失敗は分からない。CPU 使用率やキュー長は原因調査・予兆の補助に使う。

同じ期間に受け付けた予約を追い、完了期限を過ぎてから成功率を評価する。依存先の失敗も含め、まだ期限内の予約を失敗に数えない。
遅延は受付から確定までを測り、平均だけで一部の長い待ち時間を隠さない。

## 要求ゼロ・欠損・停止を見分ける

| 状況 | 判断例 |
| --- | --- |
| 週末に受付ゼロ、計測は継続 | 成功率は評価対象なし。要求ゼロだけで異常とはしない |
| 指標の更新が途絶えた | 正常・復旧とは判定せず、別の観測経路でサービスと計測系を確認する |
| 受付は続くが確定せず、最古の待機時間が増える | 処理の停滞を疑い、利用者の待ち時間と完了期限から通知を判断する |

## SLO を通知へつなぐ

失敗率で表せる SLI では、バーンレートは「観測した失敗率 ÷ 許容失敗率」。
短い窓と長い窓を組み合わせ、急激な悪化と持続する悪化を捉える。
窓・閾値は、許容する予算消費と対応時間から選び、参考資料の値をそのまま採用しない。
SLO が未合意でも、既知の重大な失敗の検知まで保留する必要はない。

## 通知を見直す

CPU が一時的に高いだけなら観察で済む場合がある。一方、利用者への影響がまだなくても、容量枯渇までの猶予が対応時間より短いなら通知候補になる。
通知数の削減だけを成功条件にせず、見逃しと検知時間が悪化しないか確かめる。

基礎となる考え方は [Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)、
SLO に基づく通知は [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) を参照する。
