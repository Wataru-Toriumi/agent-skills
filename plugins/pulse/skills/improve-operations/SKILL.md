# 運用を改善する

変更によって減らす影響・負荷を先に示し、小さく試して効果を確かめる。
個別障害の原因分析は write-postmortem、発生中の障害対応は respond-to-incident で扱う。

## 現状と改善候補を捉える

- 対象サービスと評価期間を定め、障害、通知、手作業、問い合わせ、容量・費用のうち依頼に関係する記録を読む。件数だけでなく、利用者への影響・対応時間・作業頻度を確認する。
- 反復し、サービスの成長とともに増える手作業（トイル）を、判断が必要な作業や一度限りの改善と分ける。記録がなければ効果を断定せず、先に測る項目を決める。
- 対象の廃止・簡素化・手順改善・自動化を比較する。繰り返される負荷に加え、低頻度でも影響の大きいリスクを候補に残す。

## 優先度と実験を決める

1. **便益を示す:** 利用者への影響、削減する対応時間、容量の余裕など、改善前後を比較できる指標を選ぶ。実測・推定・目標を区別する。
2. **負担を比べる:** 導入・保守コスト、失敗時の影響、必要な権限・依存作業を考慮して順序を決める。基準のない点数で順位を正当化しない。
3. **小さく試す:** 対象範囲、担当、完了条件、観測期間、戻す条件を定める。通知削減なら見逃し、自動化なら誤処理や例外対応を併せて評価する。
4. **結果を判断する:** 同じ定義の指標で比較し、件数や負荷の変化などの交絡を確認する。未実施なら計画と明示し、結果に応じて採用・修正・撤回を選ぶ。

トイルの見積もりと改善例は [改善の判断例](references/improvement-example.md) を参照する。

## 次の行動を返す

優先順に「問題と根拠／改善による便益／最小の変更／効果と悪影響の確認方法」を示す。
見送る候補には理由と再評価の条件を付け、採用した改善は監視・手順・担当へ反映する作業を含める。
小さな改善では一件の提案でよい。既定の出力先は会話。計画の依頼だけで本番を変更したり、課題を登録したりしない。
