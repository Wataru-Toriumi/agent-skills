# 改善策を要求・作業項目・実装へつなぐ

振り返りや改善計画から先へ進める場合に使う。依頼の到達点と既存の合意に合わせ、必要な工程だけを選ぶ。

## 次の工程を選ぶ

| 状況 | 引き継ぎ先と到達点 |
| --- | --- |
| 処理量・復旧時間・当番体制の実績から、設計で採用した方式を維持できるか確かめたい | 利用可能な `ink` の `review-design` に、元の設計判断と前提、観測条件・実測値・出典、再評価したい問いを渡す。指摘と未確認事項を改善候補の採否に反映する |
| 影響する利用者、必要な振る舞い、原因の仮説などが曖昧 | 利用可能な `ink` の `clarify-requirements` で、事実・仮説・未決の要求を整理する |
| 改善する範囲が決まり、実行単位や受け入れ条件を整えたい | 利用可能な `ink` の `write-work-item` で、改善策を作業項目にする |
| 一件の範囲と受け入れ条件が揃い、実装も依頼に含まれる | 利用可能な `forge` の `implement-work-item` へ渡す。文書を作り直すためだけに ink を挟まない |

原因が未確定なら、特定の修正で解消すると決めず、仮説を確かめる調査項目と、原因によらず採用できる改善を分ける。
原因調査を要求整理で済ませたことにはしない。調査項目には調べる問い、必要な証拠、終了条件を置く。
複数候補が未採用なら、すべてを実装対象にせず、採否と判断の根拠を残す。

## 根拠と条件を渡す

既存の記録・課題への参照を使い、選んだ改善策ごとに次を引き継ぐ。小さな変更は会話内で整理してよい。

- **問題と出所:** 障害・改善策の既存 ID、対象サービス、影響、発生条件、記録や指標への参照。観測事実と原因の仮説を区別する。
- **範囲と採否:** 目指す変化、採用済みの対策と理由、対象・対象外、依存作業。担当・期限・制約の合意状況と未決事項を残す。
- **受け入れ条件:** どの前提・操作で何が観測できれば変更を受け入れるか。再発経路に加え、改善によって損ねてはいけない振る舞いや副作用を含める。未合意の条件は候補と示す。
- **効果の確認:** 指標の定義、比較元の値と期間、目標と根拠、適用後の観測期間、悪影響の確認方法、見直し・切り戻しを判断する条件。未計測・未合意の値は未定とする。
- **依頼の到達点:** 要求整理、作業項目の草案、実装・検証、PRなど、今回どこまで進めるか。外部登録・公開・本番操作の許可は元の依頼から引き継ぐ。

引き継ぎ先で条件を具体化したら、元の影響・制約・対策と照合する。指標が未定であることだけで、独立して実装できる変更まで止めない。
連携先が利用できなければ、同じ情報を既存の書式や会話に整理して依頼範囲を進める。PRD・チケットの新設やプラグインの導入を前提にしない。
既に実装やPRまで依頼されていれば、その範囲で続ける。振り返り・計画だけの依頼では、次の作業候補を返す。

## 実装後の情報を受け取る

forge から対象の版・差分・受け入れ条件の検証結果・適用状況・残るリスクを受け取り、元の改善策へ対応付ける。
実装済み・適用済み・効果確認済みを分ける。PR作成やテスト成功だけで、再発防止や負荷削減を達成したとしない。
効果評価も依頼され、適用後の観測データが揃えば `improve-operations` で評価する。未適用や観測不足なら、必要なデータ・観測期間・担当を残して引き継ぐ。確認のために本番へ自動適用したり、観測期間が過ぎるまで待ち続けたりしない。
