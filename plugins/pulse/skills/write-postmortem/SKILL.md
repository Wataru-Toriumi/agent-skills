# 障害を振り返る

当時の情報と制約から経緯を説明し、再発や影響を減らす行動につなげる。
[Blameless postmortem](https://sre.google/sre-book/postmortem-culture/) の考え方を使い、個人の注意不足で分析を終えない。

## 事実と要因を整理する

1. **影響を確かめる:** どの利用者・機能に、どの期間、どの程度の影響があったかを記録や計測結果から示す。影響の開始、検知、軽減、復旧の時刻を区別し、欠けた記録は不明とする。
2. **経緯を再構成する:** 判断に影響した出来事と操作を時系列に並べる。出典とタイムゾーンを残し、記録の矛盾や当時分からなかった情報を示す。
3. **要因を追う:** 発端、影響を拡大した条件、検知・復旧を遅らせた要因を分ける。相関だけで原因を断定しない。原因の数や「なぜ」を問う回数をあらかじめ決めず、記録から要因をたどる。
4. **対策を選ぶ:** 各要因に、予防・早期検知・影響軽減・復旧短縮の対策を結び付ける。有効だった仕組みも残し、仕組みや手順を変えずに「周知・注意する」だけで閉じない。

原因が未確定でも記録を作り、残る仮説と検証方法を示す。復旧したことを、原因が解消した証拠にしない。

## 短くまとめる

説明の推敲・図解が必要な場合や、発表資料・HTML の説明ページを求められた場合は、[sketch との連携](references/sketch-collaboration.md)に従い、利用可能なスキルで整えて元の内容と照合する。

既存の書式に合わせ、必要な内容をまとめる。

- 概要・影響と、主要な出来事の時系列。
- 寄与要因とその根拠、有効だった対応。詳細なログは参照先を示す。
- 改善策と未解決事項。各改善策には優先度の理由、担当、期限、完了条件を記す。担当や期限が未合意なら、候補・未定と明示する。

既定の出力先は会話。指定があれば保存する。公開・課題登録は依頼の範囲で行う。
複数の障害や運用負荷を横断して優先度を決める場合は [improve-operations](../improve-operations/SKILL.md) を使う。
個別の改善策を要求・作業項目・実装へ進める場合は、[改善策の引き継ぎ](../improve-operations/references/implementation-handoff.md)に従い、依頼の到達点まで進める。
