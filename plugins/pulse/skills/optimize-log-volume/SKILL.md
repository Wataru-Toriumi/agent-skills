# ログ量を最適化する

## 削減対象を特定する

- 対象のサービス・環境・期間を決め、出力量、取り込み量、保存量、費用のどれを減らすか確認する。出力元から転送先・保存先までをたどり、目的に合う計測地点を選ぶ。
- イベントの種類や出力元ごとに件数と総バイト数を比べる。頻繁に出るログ、1件が大きいログ、重複して届くログを見つける。利用量が変動する場合は、リクエストやジョブあたりのバイト数も比べる。
- 実測値がなければ、コードや転送設定から候補を挙げ、必要な集計を示す。ログの抜粋だけで全体の構成比や削減額を断定しない。

## 用途に合う削減策を選ぶ

各ログを使う通知・集計・障害調査を特定する。監査用の記録は、全件保存の要否と保持期間を確認する。削ると何が分からなくなるかを示し、用途が不明なら判断を保留する。

| 量が増える要因 | 削減策と残す記録 |
| --- | --- |
| 同じイベントを複数の経路で記録・転送している | 重複する経路を整理する。残す経路で原因と対象を追え、必要な宛先に届くかを確かめる。 |
| 正常時の詳細ログが多い | 対象イベントのログレベル変更・集約・サンプリングを比べる。個別に追う失敗は残し、全件数を使う通知や成功率の分母への影響を確認する。 |
| 本文が長い、または同じ項目を繰り返している | 調査に使わない項目を省き、処理を結び付ける識別子と結果を残す。残った項目で代表的な問い合わせに答えられるか試す。 |
| 用途に比べて保存期間が長い | 調査でさかのぼる期間と監査の保持要件を満たす範囲で、保存先や期間を見直す。期間短縮が効くのは保存量だけで、取り込み量は変わらない。 |

イベントごとに変更箇所、残す記録、削減見込みと根拠を示す。変更する地点のバイト数から見積もり、複数の対策で重なる削減分は一度だけ数える。費用は課金単位と単価が分かる範囲で見積もる。

## 削減手順

分析・提案の依頼では、選んだ削減策と以下の手順に沿った検証計画を返す。

1. **変更前の状態を記録する。** 同じ期間のログ件数・バイト数・処理件数を集計する。現在の設定、残す記録、中止条件、設定の戻し方を控える。
2. **対象を絞って試す。** 代表ログや検証環境で対策を試す。たとえば正常終了イベントを二重に転送しているなら、片方の経路でそのイベントだけを転送対象から外す。
3. **削減効果と記録の欠落を確かめる。** 同程度の処理量で変更前後のバイト数を比べる。重複転送の例なら、残した経路で正常終了の全件を追えるか確認する。影響を受ける通知・障害調査・監査でも、必要な記録を使えるか確かめる。
4. **本番適用も依頼された場合は、段階的に広げる。** 試行で削減効果と必要な記録の両方を確認できたら、同じ指標を観測しながら適用範囲を広げる。中止条件に達したら展開を止め、設定を戻す。削減実績は適用後の観測値から報告する。

既存ログの削除は、削除自体が依頼に含まれる場合に限る。設定を戻しても、未収集・削除済みの記録を復元できるとは限らない。
