# コードをリファクタリングする

変更しづらさの原因と改善の効果を示してから、振る舞いを維持できる小さな段階で構造を変える。
調査や提案だけの依頼では編集しない。機能追加・不具合修正も依頼されている場合は、構造変更と区別して進める。

## 目的と守る振る舞いを決める

- リポジトリの指示、作業ツリー、呼び出し元・依存先・テストを確認し、既存の変更を保持する。
- 入出力、公開 API、例外、副作用の回数・順序、保存形式と、互換性・性能の制約を維持条件にする。
- 現行動作と仕様の違いは不具合として分け、修正の依頼がなければ報告に留める。

## 改善候補を絞る

- 予定する変更や繰り返し困る作業を起点に、負担の根拠・期待する効果・影響範囲・検証コストを比べる。関数の長さや重複の数だけで優先しない。
- 依頼を満たす最小の範囲を選び、採用・見送りの理由を示す。効果が曖昧、コストに見合わない、将来の推測しかない候補は縮小するか見送る。

比較の例は [候補の優先順位](references/decisions.md#候補の優先順位)を参照する。

## 着手前に効果を示す

編集前に、次の3点を会話で短く示す。計画書は必須にしない。

- **現状の負担**：どの作業が難しいかと、コード上の根拠。
- **変更と効果**：何を変え、修正箇所や検証の準備がどう減るか。
- **コストと確認方法**：影響範囲、増える複雑さ、効果と振る舞いの確認方法。

事実と期待を分け、未計測の時間短縮や不具合削減を断定しない。行数や抽象化の数だけを成果にしない。
実装まで依頼されていれば説明後に進め、提案の確認を求められている場合は返答を待つ。

## 変更を組み立てる

抽出・インライン化・移動などを目的に合わせて選ぶ。迷う場合は [変更の判断例](references/decisions.md) を参照する。

- 同じ理由で変わる処理をまとめ、見た目の類似だけで共通化しない。
- 各段階で検証できる順序にする。境界をまたぐ場合は、必要に応じて互換用の入口を残し、呼び出し元を移してから除く。
- フレームワークの導入、公開契約の変更、データ移行は、依頼の範囲を確認して扱う。

## 少しずつ変更して確かめる

1. 変更前に関連箇所を検証し、既存の失敗を把握する。検証が足りなければ、代表入力や境界値で変更前後を比較できるようにする。
2. 構造を一段階ずつ変え、型・参照関係と影響する振る舞いを確認する。結果が変わったら原因を調べ、期待値の変更で差を隠さない。自分の直近の変更を調整する際も既存の作業を巻き戻さない。
3. 内部名や配置に依存するテストは追従させ、元の契約のアサーションを残す。カバレッジやスナップショット更新だけで同等性を判断しない。
4. 着手理由にした作業をたどり、修正箇所や検証の準備がどう変わったかを確認する。目的を達成したら止め、関連する検証と必須チェックを実行する。

同等性を確かめられない変更は保留し、必要な検証を示す。独立して検証できる範囲は進める。

## 結果を伝える

確認できた効果と検証結果を、未確認の期待・経路と分けて報告する。未解決事項や別途扱う不具合・仕様変更も添える。
コミット・PR も依頼されていれば [commit-changes](../commit-changes/SKILL.md)・[create-pr](../create-pr/SKILL.md) に従い、独立した構造変更と振る舞いの変更を分ける。
