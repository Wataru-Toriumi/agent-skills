# コードをリファクタリングする

変更しづらさの原因と改善の効果を示してから、振る舞いを維持できる小さな段階で構造を変える。
調査や提案だけの依頼では編集しない。機能追加・不具合修正も依頼されている場合は、構造変更と区別して進める。

## 目的と守る振る舞いを決める

- リポジトリの指示と作業ツリーを確認し、対象の呼び出し元・依存先・テストを読む。既存の未コミット変更を保持する。
- 対象に関係する入出力、公開 API、例外、副作用の回数・順序、保存形式を確認する。互換性や性能の制約がある場合は、それも維持条件に含める。
- 現行動作と期待仕様が違う場合は不具合として分ける。修正の依頼がなければ、リファクタリングに紛れ込ませず報告する。

## 着手前に効果を示す

編集を始める前に、次の内容を会話で短く示す。小さな変更なら数文でよく、計画書は必須にしない。

- **現状の負担**：どの作業で何が難しいかを、対象コードや呼び出し関係を根拠に説明する。
- **変更と期待する効果**：何を変えると、どの作業がどう楽になるかを結び付ける。「保守性が上がる」だけで済ませず、修正箇所がまとまる、外部サービスなしで計算を検証できる、といった変化を示す。
- **コストと確認方法**：変更が及ぶ範囲や増える複雑さを示し、効果と振る舞いの維持をそれぞれどう確かめるかを説明する。

実測した事実と期待を分け、未計測の時間短縮や不具合削減を数値で断定しない。行数や抽象化の数だけを成果にしない。
効果を具体的に説明できない場合や、負担が効果に見合わない場合は、範囲を縮めるか見送り、理由を示す。
実装まで依頼されていれば説明後に進め、提案への確認を求められている場合は返答を待つ。

## 変更を組み立てる

目的に応じて、抽出・インライン化・移動・依存方向の整理などを選ぶ。
効果の伝え方や手法の選択に迷う場合は [変更の判断例](references/decisions.md) を参照する。

- 変更後も同じ理由で変わる処理をまとめる。見た目が似ているだけの処理や、将来の用途を想定した共通化は避ける。
- 一段階ごとに実行・検証できる順序にする。境界をまたぐ変更では、必要に応じて互換用の入口を残し、呼び出し元を移してから不要な入口を除く。
- 局所的な整理だけで目的を達成できるなら、範囲をそこで止める。新しいフレームワーク、公開契約の変更、データ移行が必要なら、当初の依頼との関係を整理してから扱う。

## 少しずつ変更して確かめる

1. 変更前に関連箇所を検証し、既存の失敗と今回の回帰を区別できる状態にする。振る舞いの手掛かりが足りない箇所は、代表入力や境界値で変更前後を比較できる検証を用意する。
2. 構造を一段階ずつ変え、型・参照関係と影響する振る舞いを確認する。結果が変わったら原因を調べ、期待値の変更で差を隠さない。自分の直近の変更を調整する際も既存の作業を巻き戻さない。
3. テストが内部の名前や配置に依存している場合は追従させ、元の契約を確かめるアサーションを残す。カバレッジの数値やスナップショット更新だけで同等性を判断しない。
4. 事前に示した効果を確認し、目的を達成したら変更を止める。関連する検証とリポジトリの必須チェックを実行する。未検証の経路があれば明示し、振る舞いを維持できたと断定しない。

検証手段がなく同等性を判断できない変更は保留し、必要な検証と理由を示す。独立して確かめられる範囲は進める。

## 結果を伝える

事前に示した効果に対し、確認できた改善と未確認の期待、振る舞いの検証結果を短く報告する。
未解決事項や、別途扱う不具合・仕様変更があれば添える。
コミットや PR 作成も依頼されている場合は [commit-changes](../commit-changes/SKILL.md)・[create-pr](../create-pr/SKILL.md) に従い、独立した構造変更と振る舞いの変更を分ける。
