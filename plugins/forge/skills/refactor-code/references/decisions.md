# 変更の判断例

## 候補の優先順位

料金改定を控え、「請求処理を変更しやすくしたい」と依頼された架空の例。

| 候補 | 確認できた負担とコスト | 判断 |
| --- | --- | --- |
| 同じ割引ルールを集約する | 前回も今回も3箇所が改定対象。境界値のテストがある | 改定に直結するため優先する |
| 長い集計関数を分割する | 改定対象ではなく、具体的な読みづらさも未確認 | 長さだけで着手しない |
| 決済サービスを抽象化する | 切り替え予定はなく、境界とテストが増える | 見送る |

テストの不足は検証コストに含め、それだけで低優先にはしない。3箇所が別々の仕様として変わるなら、共通化は見送る。

完了時は、改定対象の判定が一箇所になり、各呼び出し元の境界値の結果が変わらないことを確認する。改定そのものは実装しない。

## 着手前の説明例

以下は架空の例。対象箇所や件数は、調査で確認した内容に置き換える。

> 現在は請求額の計算が送信処理に埋まり、割引条件のテストにも決済 API の代替実装が必要です。
> 計算を独立した関数にすると、金額の境界値を API の準備なしで検証できます。
> 変更は計算部分と呼び出し元に絞ります。関数は増えますが、送信の順序と失敗時の扱いは変えません。
> 計算テストが API に依存しないことを確認し、既存の結合テストで金額と送信回数を確かめてから完了とします。

完了時は「計算テストを API なしで実行できた」のように確認結果を返す。
実行時間や障害件数を測っていなければ、「テストが高速化した」「障害が減った」とは報告しない。

似た式が複数あるだけで、同じ理由で変更される根拠がない場合は共通化を見送る。
「重複を減らせる」だけでなく、変更箇所をまとめる利点が、別の仕様を結び付ける負担に見合うかを判断する。

## 手法を選ぶ

| 状況 | 候補 | 確かめること |
| --- | --- | --- |
| 一つの関数で計算と外部への送信が混ざる | 計算を抽出し、副作用を呼び出し側に残す | 戻り値、丸め、送信の回数・順序、例外時に送信されないこと |
| 同じ業務ルールの変更で複数箇所を修正する | ルールを一箇所に集める | 条件の意味や変更理由が本当に同じか。似た式でも別の仕様なら分けておく |
| 薄い関数を何段も追わないと処理が分からない | 不要な中継をインライン化する | 公開された入口や差し替えに使う境界まで消していないか |
| 内部モジュールの変更が多くの利用側へ波及する | 責務の移動や依存する窓口の整理 | 依存の循環、初期化順序、呼び出し元の互換性 |
| 関数名やローカル変数名だけが理解を妨げる | 局所的な改名で終える | 外部に公開される名前や、文字列・設定経由の参照ではないか |
| エラーを例外から戻り値へ変えたい | 振る舞いの変更として別に扱う | 呼び出し元の契約が変わるため、単なる内部整理として進めない |

## 検証が足りないコード

例えば、請求計算と決済 API 呼び出しが混ざっているなら、通常・割引境界・失敗時の金額と送信回数を変更前に確認する。
本番で決済せず、既存のテスト環境や代替実装で副作用を観測する。
計算だけを抽出して同じ検証を通し、その後に依存の整理へ進む。

現在の実装を記録するテストは、現行動作の変化を検知するために使う。現行動作が正しい仕様だと証明するものではない。
明らかな誤りは別の修正として示し、構造変更と同時に期待値を変えて見えなくしない。
