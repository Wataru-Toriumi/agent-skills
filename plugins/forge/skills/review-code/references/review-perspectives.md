# レビュー観点

変更内容に関係する行を選び、確認の手掛かりとして使う。総評で全項目を列挙する必要はない。
リポジトリの仕様や実際の利用条件を優先し、ここにある例だけで不具合と判断しない。

## 変更から選ぶ

| 変更の種類 | 確認すること |
| --- | --- |
| 入出力・条件分岐・計算 | 呼び出し元の契約、空・欠落・ゼロ・上限、単位や時刻の扱い。意図した仕様変更が利用側にも反映されているか |
| 保存・削除・外部呼び出し | アップロード・公開・通知は依頼を満たすために必要か。途中失敗で残る状態、成功を返すタイミング、取り消しや復旧、再試行による副作用の重複も確認する |
| 非同期・共有状態・キャッシュ | 実行順序、同時更新、キャンセル、ロック範囲、キャッシュのキーと無効化。処理が交差したときも前提を保てるか |
| 外部入力・認証・権限・出力 | 誰がどのデータを読み書きできるか。入力検証や対象ごとの権限確認が、変更した経路でも働くか。応答やログの閲覧者に見せてよい情報か |
| API・スキーマ・依存関係・設定 | 既存の利用側、保存済みデータ、既定値、対応環境との互換性。移行順序や新旧版の混在で壊れないか |
| ループ・検索・I/O・資源管理 | 入力件数や同時実行数に応じて処理量、メモリ、接続数、待ち時間がどう増えるか。実際の上限や計測値と照合する。取得した接続やファイルは、途中の失敗・キャンセル時にも解放されるか |
| UI・利用手順 | 読み込み・空・失敗時の表示、二重操作、入力保持、キーボード操作、ラベル。見た目や操作性を確認できない場合はその範囲を示す |
| レイヤー間の依存 | 設計文書・依存ルール・既存の実装から各層の責務と許される参照先を確かめる。差分の import、引数や戻り値の型をたどり、逆向きの依存、禁止された層の直接参照、循環依存が生じていないかを見る |
| 分割・共通化・抽象化 | 責務の分け方、重複する判断、変更時に触る範囲。現状の要件に不要な抽象化や、隠れた結合を増やしていないか |
| テスト・CI・文書・スキル | 完了として報告した動作を、実際の検証結果で裏づけられるか。期待動作が崩れたときにテストが失敗するか、モックが隠す境界、CI の実行条件、手順・例・参照先と必要な権限・前提の整合を確かめる |

テスト追加の有無だけで良否を決めない。変更した振る舞いを既存テストが検証しているか、
新たな検証が必要なら何を見落としているかを説明する。
文書やスキルは記載された手順を利用者の立場でたどり、前提の不足や矛盾を確かめる。

追加の保護が必要かは、対象と操作ごとに判断する。たとえば公開仕様どおりの情報を返す閲覧経路なら、匿名で読めること自体は問題にならない。公開対象が分からず判定を左右する場合は、許容されていると推測せず確認事項にする。

## 指摘の判定例

| 状況 | 扱い |
| --- | --- |
| 「動画を含む PPTX を1ファイルで渡す」という依頼が、Drive に動画をアップロードする手順へ案内される | 形式を選ぶ分岐をたどる。生成した PPTX が外部の動画を参照し、ファイル単体で再生できないなら、要件を満たせない理由を添えて `[must]` とする |
| 対象スライドが PPTX 内の動画を参照し、その動画が元ファイルと一致する。PowerPoint での再生は未確認と報告されている | 埋め込みは確認済みとして扱う。実機再生が受け入れ条件なら未達の検証として示し、再生できるかどうかは未確認とする |
| 所有者で絞っていた取得処理を ID のみの検索へ変更し、他の利用者のデータに到達できる | 権限確認が別の層にないことを調べ、条件と漏えいする情報を添えて指摘する |
| 所有者の確認を共通処理に移し、すべての呼び出し元が対象データを渡してその確認を通る | 同じ確認を各呼び出し元にも追加するよう求める必要はない。適用範囲が不明なら、どの経路を確認できていないかを示す |
| 一括処理を並列化し、1件につき最大1接続を使う | 同時実行数と接続プールの上限を照合する。他の処理と共有する枠や失敗時の解放も考慮し、接続待ちやタイムアウトが起きる条件を示せる場合に指摘する |
| 保存完了後の応答喪失に対して再試行を追加し、同じ処理が二重に保存される | 再試行の経路と重複を防ぐ仕組みを調べ、具体的な実行順序を示す |
| 配列の先頭を参照しているが、すべての呼び出し元で空配列を拒否している | 空配列で壊れるという指摘はしない。新しい呼び出し元が防御を迂回するなら再評価する |
| テストの追加はないが、既存テストが変更後の契約と失敗経路を検証している | テスト不足とはしない。成功結果だけでなく検証内容を読む |
| API の仕様変更が要求に明記され、利用側と移行手順も更新されている | 変更前と異なることだけを回帰としない |
| 将来増えるかもしれない呼び出し元のために汎用化したい | 現在の問題がなければ指摘を省く |
| 新しい抽象化で一つの判断が複数箇所に分散した | 追跡や変更が難しくなる箇所を示し、設計の改善提案として扱う |
| 永続化層から独立させる方針のドメイン層で、関数の戻り値に ORM の型を使い始めた | DB 操作がなくても型の参照で依存が生じる。該当する設計方針と型の定義元を示し、永続化側の型変更がどの呼び出し元に及ぶかを説明する |
