# レビュー観点

変更内容に関係する行を選び、確認の手掛かりとして使う。
リポジトリの仕様や実際の利用条件を優先し、ここにある例だけで不具合と判断しない。

## 変更から選ぶ

| 変更の種類 | 確認すること |
| --- | --- |
| 入出力・条件分岐・計算 | 呼び出し元の契約、空・欠落・ゼロ・上限、単位や時刻の扱い。意図した仕様変更が利用側にも反映されているか |
| 保存・削除・外部呼び出し | 途中失敗で残る状態、成功を返すタイミング、取り消しや復旧。再試行で副作用が重複しないか |
| 非同期・共有状態・キャッシュ | 実行順序、同時更新、キャンセル、ロック範囲、キャッシュのキーと無効化。処理が交差したときも前提を保てるか |
| 認証・権限・外部入力 | 操作対象ごとの権限、利用者やテナントの分離、入力から危険な操作までの経路。出力やログに秘密情報が混ざらないか |
| API・スキーマ・依存関係・設定 | 既存の利用側、保存済みデータ、既定値、対応環境との互換性。移行順序や新旧版の混在で壊れないか |
| ループ・検索・I/O・資源管理 | 想定件数での計算量、呼び出し回数、メモリ、資源の解放、待ち時間。性能問題は実際の利用規模や計測を根拠にする |
| UI・利用手順 | 読み込み・空・失敗時の表示、二重操作、入力保持、キーボード操作、ラベル。見た目や操作性を確認できない場合はその範囲を示す |
| 分割・共通化・抽象化 | 責務と依存の向き、重複する判断、変更時に触る範囲。現状の要件に不要な抽象化や、隠れた結合を増やしていないか |
| テスト・CI・文書・スキル | 期待動作を誤るとテストが失敗するか、モックが重要な境界を隠していないか。CI の実行条件、手順・例・参照先の整合、必要な権限や前提が保たれるか |

テスト追加の有無だけで良否を決めない。変更した振る舞いを既存テストが検証しているか、
新たな検証が必要なら何を見落としているかを説明する。
文書やスキルは記載された手順を利用者の立場でたどり、前提の不足や矛盾を確かめる。

## 指摘の判定例

| 状況 | 扱い |
| --- | --- |
| 所有者で絞っていた取得処理を ID のみの検索へ変更し、他の利用者のデータに到達できる | 権限確認が別の層にないことを調べ、条件と漏えいする情報を添えて指摘する |
| 保存完了後の応答喪失に対して再試行を追加し、同じ処理が二重に保存される | 再試行の経路と重複を防ぐ仕組みを調べ、具体的な実行順序を示す |
| 配列の先頭を参照しているが、すべての呼び出し元で空配列を拒否している | 空配列で壊れるという指摘はしない。新しい呼び出し元が防御を迂回するなら再評価する |
| テストの追加はないが、既存テストが変更後の契約と失敗経路を検証している | テスト不足とはしない。成功結果だけでなく検証内容を読む |
| API の仕様変更が要求に明記され、利用側と移行手順も更新されている | 変更前と異なることだけを回帰としない |
| 将来増えるかもしれない呼び出し元のために汎用化したい | 現在の問題がなければ指摘を省く |
| 新しい抽象化で一つの判断が複数箇所に分散した | 追跡や変更が難しくなる箇所を示し、設計の改善提案として扱う |
