# Review code

変更によって発生する具体的な問題を見つけ、修正判断に必要な根拠を示す。
読みやすさや設計のレビューが指定された場合は、その観点に合わせる。
通常のレビューでは、動作の正しさ、回帰、データ損失、セキュリティ、互換性への影響を優先する。

## 範囲と根拠

- PR・コミット範囲・作業ツリーなど、指定された対象と比較元を特定する。PR なら base/head と merge-base を確認する。
- 作業ツリーが対象なら、ステージ済み・未ステージ・未追跡の変更を含めて調べる。指定範囲を超えて既存の問題を列挙しない。
- 差分だけで結論を出さず、周辺コード、呼び出し元、型、テスト、設定から実際に到達する条件を確かめる。
- 検証が必要なら対象を絞ったテストや再現手順を使う。通常のレビュー中にファイルを修正したり、実環境のデータを変更したりしない。
- 断定に必要な情報がなければ仮定や質問として区別し、推測を不具合として報告しない。

## 指摘をまとめる

各指摘に次を含め、重要度の高い順に示す。

- 問題が分かる短いタイトルと重要度。既存の基準がなければ、P0 は広範で即時対応が必要な重大障害、P1 は次のリリース前に修正したい重大な問題、P2 は通常の修正対象、P3 は影響が小さい問題とする。
- 対象ファイルと最小限の行位置。PR では可能な限り変更行に紐づける。
- 問題が発生する入力・状態・実行経路と、利用者やシステムへの影響。
- 根拠となるコードや再現結果。必要なら修正の方向性を短く添える。

単なる好み、確認できない可能性、別の指摘と同じ原因の重複は減らす。
指摘数を埋めるために問題を作らない。指摘がなければその旨を明記し、確認範囲と残る検証上の限界を示す。

## 出力先と操作

指摘を先に、その後に未解決の前提や検証結果を簡潔に報告する。
既定の出力先は会話。GitHub へのコメント・レビュー送信は依頼がある場合だけ行い、approve / request changes の指定や意図を尊重する。
レビューの依頼だけで、コード修正・コミット・マージまで進めない。
