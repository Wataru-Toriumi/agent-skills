# Review code

変更によってどんな条件で問題が起きるかを調べ、修正が必要か判断できる根拠を示す。
読みやすさや設計のレビューが指定された場合は、その観点に合わせる。
通常のレビューでは、動作の正しさ、回帰、データ損失、セキュリティ、互換性への影響を優先する。

## 範囲と期待動作を確かめる

- PR・コミット範囲・作業ツリーなど、指定された対象と比較元を特定する。PR なら base/head と merge-base を確認する。
- 作業ツリーが対象なら、ステージ済み・未ステージ・未追跡の変更を含めて調べる。指定範囲を超えて既存の問題を列挙しない。
- リポジトリの指示、要求、公開仕様から期待動作を把握する。変更前の動作やテストだけを正解とせず、意図した仕様変更と回帰を区別する。
- 変更に関わる代表的な依頼を一つ選び、利用者が普段使う入口から操作をたどる。途中の選択や既定値を経て、利用者が期待する結果を得られるか確かめる。
- 差分全体を確認し、呼び出し元・データの保存先・外部との境界まで影響を追う。生成物は生成元と対応を確認する。確認できない範囲は結果に残す。

## 変更に合う観点で調べる

PR の変更種別は、タイトルやラベルを参考に、要求と差分から判断する。変更が混在する場合は、該当する観点をすべて確認する。文書や CI 設定など、表に当てはまらない変更は、その目的と影響を示す。

| 変更種別 | 確認すること |
| --- | --- |
| tidy（局所的な整理） | 改名や条件式の整理で、参照先・分岐結果・評価順・副作用が変わっていないか。 |
| refactor（構造の変更） | 責務や依存先を移した後も、呼び出し元から見た入出力・例外・副作用が保たれるか。 |
| 機能追加 | 新しい操作は要求や受け入れ条件を満たすか。既存の使い方にどんな影響があるか。 |
| バグ修正 | 元の発生条件で期待どおりに動くか。関連する正常なケースも引き続き動くか。 |

[レビュー観点](references/review-perspectives.md)から変更に関係する項目を選び、影響の大きい箇所から調べる。
変更に関係のない観点や、指摘がない項目を埋める必要はない。

- 正常系に加え、境界値・失敗・再実行・並行実行のうち、変更に関係する経路を追う。
- 周辺コード、呼び出し元、型、テスト、設定を読み、問題の条件が成立するか、既存の防御で防がれていないかを確認する。
- 必要なら対象を絞ったテストや再現手順で確かめる。実行結果とコードを読んだ判断を区別する。テストや lint の成功だけでレビュー済みとしない。

契約・論理制約・並行実行などの性質を機械的に検証する必要があれば、利用可能な `probe` の `verify-formally` に対象の版・コード・要求・仮定・検証する性質を渡す。
レビューの操作範囲を保ち、返された反例が実際のコードで成立するかと、保証の範囲を確認する。利用できない場合もレビューを続け、必要な検証と未確認の性質を残す。

## 指摘にするか判断する

不具合として報告する前に、次を確かめる。

- 今回の変更で問題が生じるか、既存の問題が悪化するか、その問題に至る新しい経路ができている。
- 発生条件と期待動作との差を、コード・仕様・再現結果で説明できる。実行できなくても、経路を根拠として示せるなら指摘できる。
- 利用者や運用への影響と、修正すべき箇所が具体的である。

根拠が足りないものは不具合と断定せず、判断に必要な確認事項として分ける。
設計・可読性の改善は、責務の混在や変更の波及など具体的な負担を示し、不具合と区別する。
好みだけの命名・整形、将来の仮定だけに基づく汎用化、同じ原因の重複指摘は省く。

## 指摘をまとめる

説明の推敲・図解が必要な場合や、発表資料・HTML の説明ページを求められた場合は、[sketch との連携](../create-pr/references/sketch-collaboration.md)に従い、利用可能なスキルで整えて元の内容と照合する。

- マージ前の修正が必要なら、指摘の先頭に `[must]` を付け、理由を示す。会話でのレビュー結果、PR コメント、草案のいずれにも適用する。
- その他の PR コメントや草案には、意図に応じて `[nits]`・`[imo]`・`[question]`・`[issue]` を付ける。

使い分けは [コメントの接頭辞](references/comment-prefixes.md) に従い、既存の書式指定がある場合はそちらを優先する。

各指摘に次を含め、重要度の高い順に示す。

- 問題が分かる短いタイトルと重要度。既存の基準がなければ、P0 は広範で即時対応が必要な重大障害、P1 は次のリリース前に修正したい重大な問題、P2 は通常の修正対象、P3 は影響が小さい問題とする。影響と発生条件で決め、不確かな推測を低い重要度の不具合として扱わない。
- 対象ファイルと、問題を示す最小限の行範囲。
- 問題が発生する入力・状態・実行経路と、利用者やシステムへの影響。
- 根拠となるコードや再現結果。必要なら修正の方向性を短く添える。

指摘がなければその旨を明記する。確認範囲、実施した検証、未確認の経路を簡潔に添え、無欠陥とは断定しない。

## PR を承認できるか判断する

総評には、レビューした head SHA、該当する変更種別、PR 全体の判定とその理由を書く。

| 判定 | 判断基準 |
| --- | --- |
| 要修正 | マージ前に直すべき問題がある。該当する `[must]` の指摘を示す。 |
| 保留 | 必要な仕様や検証結果が不足しているか、リポジトリが求める担当者の判断や独立レビューを待っている。何を確認すれば判定できるかを示す。 |
| Approve 可 | 対象の head で各変更種別の判断に必要な根拠がそろい、承認を妨げる問題がない。任意の改善提案は残してよい。 |

## 出力先と操作

不具合の指摘を先に、その後に確認事項・改善提案・検証結果を簡潔に報告する。該当しない区分は省く。
既定の出力先は会話。GitHub へのコメントやレビューは依頼された範囲で送る。
承認の依頼があり、対象 PR を承認できるアカウントを使い、最新の head を「Approve 可」と判定した場合にのみ Approve を送る。
PR 作成者本人のアカウントを使う場合やセルフレビューでは、判定を会話で報告する。

GitHub へ投稿する場合は、次の配置にする。

- 各指摘は、該当する差分の行または最小限の行範囲へ個別のレビューコメントとして投稿する。独立した指摘を一つのコメントにまとめない。
- 特定行に結びつかないファイル全体の指摘は、そのファイルへのコメントにする。PR 全体に関わる内容とレビュー範囲・検証結果だけを総評に書き、個別指摘の全文を重複して載せない。
- 投稿前に最新の head と差分を確認する。head が変わっていれば、追加差分をレビューして承認可否を判定し直す。行にコメントする際は、対象ファイル・行範囲・追加側か削除側かを確認し、同じ論点の既存スレッドがあればそこへ返信する。
- ツールや権限の制限で該当箇所に投稿できない場合は、その旨と対象ファイル・行範囲・コメント案を会話で返す。総評への一括投稿で代用して、個別投稿済みとは扱わない。
- 投稿後にコメント本文と紐づいた箇所を確認し、未送信の指摘があれば明示する。

レビュー中に対象ファイルや実環境のデータを変更しない。再現が必要なら一時環境を使う。
レビューの依頼だけで、コード修正・コミット・マージまで進めない。create-pr のセルフレビューでも、修正はレビュー後の手順で扱う。
