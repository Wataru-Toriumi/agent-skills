# 整理するかの判断例

| 状況 | 判断 | 注意点 |
| --- | --- | --- |
| 次に直す条件式の意味が読み取りづらい | 先に条件へ名前を付ける | 短絡評価や例外の発生条件、呼び出し回数を変えない |
| 深いネストで通常処理が見つけづらい | 早期 return を検討する | 後続の監査ログや後処理を省略するなら、その変換は採用しない |
| 関連する処理が離れており、変更箇所を見落とす | 関連箇所を近くに置く | 実行順序、変数のスコープ、モジュール初期化の副作用を保つ |
| 機能の追加中で、処理の共通部分がまだ定まらない | 動く変更ができてから整理する | tidy だけの依頼なら、機能を先に実装せず後で整える理由を示す |
| 短い式を一度使うだけで、意味も明確 | 今回は見送る | 関数や変数を増やすこと自体を成果にしない |
| 未使用に見える公開関数を見つけた | 利用の有無を確認するまで削除しない | リポジトリ内の検索だけでは外部利用や動的な参照を否定できない |
| 局所的な整理のために依存関係全体の組み替えが必要 | 広がる範囲と理由を示し、依頼範囲を見直す | 当初の範囲で整えられる箇所は進め、構造改善には refactor-code を使う |

例えば、支払い条件を追加する前に既存の条件へ名前を付ければ、整理の差分と新条件の差分を別々に確認できる。
一方、名前を付けるために条件式を短絡評価の外へ移すと、それまで実行されなかった問い合わせが走る場合がある。
見た目の簡潔さより、同じ入力で同じ振る舞いになることを優先する。
