# コードを小さく整える

今の理解や次の変更を妨げる箇所を、効果を確かめられる範囲で整える。
tidy はリファクタリングの一部として扱い、少ない行数でも振る舞いを変える修正は区別する。

## 整える範囲とタイミングを選ぶ

- リポジトリの指示、作業ツリー、対象コードと利用箇所を確認する。調査や提案だけの依頼では編集しない。
- 次に行う変更、または現在読みづらい理由を特定する。名前、条件分岐、処理の配置などから、その妨げを減らす変更だけを選ぶ。
- **先に整える**：予定する変更が簡単になり、準備のコストに見合う。
- **後で整える**：動く変更を見てからの方が、まとめる処理や適切な名前を判断しやすい。
- **今回は見送る**：既に読み取れる、効果が小さい、または安全な検証に大きな準備が必要。変更なしという結論も許容する。

依頼が tidy のみなら、後で行う機能追加まで実装しない。
対象が広がる場合や選択に迷う場合は [整理するかの判断例](references/decisions.md) を参照する。

## 小さく変えて確かめる

1. 編集前に、現状の負担・変更による効果・確認方法を数文で示す。例えば「購入可否の条件が埋もれているため、条件に名前を付けて判断箇所を追いやすくする。呼び出し側から条件の意味が分かることと、境界値での結果が同じことを確かめる」とする。効果を説明できなければ見送る。
2. 変更に合う既存の検証を選び、変更前の状態を確認する。単純な改名なら参照・型・既存テスト、条件や順序を触るなら境界値・評価順・副作用を確かめる。
3. 一つの意図で編集し、振る舞いが維持されるかを確かめる。早期 return による後処理の省略、式の移動による評価回数の変化、公開名の変更に注意する。
4. 妨げが解消したら止める。周辺の好みによる整形や抽象化を連鎖させず、リポジトリの必須チェックを実行する。

整理だけを確かめるテストを機械的に追加しない。既存の検証で見落とす振る舞いがあり、今回の変更に必要なら補う。
検証が失敗したら既存の失敗と今回の差を調べ、期待値の書き換えで通さない。安全に進められない範囲は保留し、既存の作業を保持する。

## 結果を伝える

事前に示した効果に対し、確認できた改善と検証結果を短く報告する。未確認の効果や、見送った理由があれば添える。
コミットも依頼されている場合は [commit-changes](../commit-changes/SKILL.md) に従い、整理と機能変更を独立して確認できる単位に分ける。
1回の編集ごとにコミットする必要はない。
