# sketch と連携して変更・レビューの説明を整える

内容の判断と根拠を整理した後、必要な推敲・図解や、依頼された形式への変換に、利用可能な `sketch` のスキルを使う。
表現の変更が不要ならそのまま返し、同じ文章を工程ごとに推敲し直さない。

## 表現を選ぶ

| 必要なこと | スキル |
| --- | --- |
| 日本語の重複・構成・言い回しを整える | `polish-writing` |
| 関係・状態・操作順を図で説明する | `draw-mermaid` |
| Marp の発表資料を作る依頼に応える | `create-marp-slides` |
| HTML の説明ページを作る依頼に応える | `explain-visually` |

指定された書式・出力先を優先する。文章やレビューの依頼だけで、スライド・HTML・別の保存ファイルを増やさない。
スキルが利用できなくても、元の作業を続け、必要な文章や表で説明する。自動でインストールしない。

## 渡して照合する

1. 読者・理解や判断してほしいこと、対象の本文や資料、変更する範囲、出力形式・保存先を渡す。元資料の参照先と、確定事項・提案・未確認の区別を添える。
2. 対象の差分・SHA、変更理由、検証結果と未実行項目、残るリスクを渡す。PR は提出先のテンプレート、レビューや返信は指摘の対象・発生条件・根拠・優先度と対応状況も保持する。
3. 整えた本文・図などと、内容上の確認事項・描画や検査の実施状況を受け取る。変更内容と対象の版が一致し、未実行を成功、ローカルの修正を反映済みと表現していないか確認する。指摘の深刻さや対応方針を文章の調整で変えない。
4. 元のスキルで必要な項目と書式を確認して成果物へ反映する。内容の矛盾は元の要求・差分・記録へ戻して判断し、表現の調整だけで解消したことにしない。描画や文章検査の成功を、内容の正しさや検証の成功に置き換えない。

投稿・公開・通知などは、元の依頼で認められた範囲のまま扱う。
