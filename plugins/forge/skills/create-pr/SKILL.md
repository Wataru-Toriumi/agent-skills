# Create PR

レビューする人が、解決する問題・変更後の動作・検証結果を把握できる PR を作る。
説明文の草案だけの依頼なら、リモートへの書き込みは行わない。

## 差分と送り先を確かめる

- リポジトリの指示と PR テンプレートを読む。remote、現在のブランチ、作業ツリー、既存 PR を確認する。
- base はユーザー指定を優先し、指定がなければリポジトリの既定ブランチを使う。fork の場合は提出先と push 先を区別する。
- base の最新情報を取得し、merge-base から head までの差分とコミットを確認する。未コミットの変更も調べ、依頼対象を漏らしたり、無関係な変更を混ぜたりしない。
- 既定ブランチ上に変更がある場合は作業ブランチを作る。別作業の変更や既存ブランチを壊さずに進めるため、必要なら worktree を使う。競合解消などで意図が判断できない場合だけ確認する。

## レビューできる状態にする

1. 対象の変更に必要な検証を行う。既存の結果を使う場合は、検証後に対象が変わっていないことを確認する。
2. 依頼対象に未コミットの変更があれば、差分を確認して意味のある単位でコミットする。無関係なステージ済み変更も含めない。
3. 作業ブランチを適切な remote に通常の push で送る。PR 作成に必要なコミット・push は依頼の範囲として進める。拒否された push を force で迂回せず、原因を確認する。
4. 同じ head と base の PR があれば更新し、重複して作らない。draft の指定に従い、実装が未完了ならその状態を明示した draft にする。

利用できる GitHub 接続ツールや CLI を使う。認証や権限が足りない場合は、完成したタイトル・本文と未完了の操作を示す。
マージやレビュー依頼の送信は、別途依頼された場合に行う。

## タイトルと本文

- タイトルは変更の成果を短く表す。本文は具体的な問題と変更後の動作から始め、必要なら発生条件や変更前後の例を添える。
- レビュー判断に必要な実装上の選択、互換性への影響、移行手順だけを含める。作業中の会話や採用しなかった案の羅列は省く。
- 検証は実行した内容と結果を記載し、未実行・失敗・未解決事項を区別する。既存 PR の更新時も最終差分に合わせてタイトルと本文を見直す。
- リポジトリにテンプレートがあれば使い、なければ短い説明と検証結果で十分。小さな変更に大きな定型文を付けない。
- 複数行の本文は構造化された引数、または一時ファイルと CLI の本文ファイル指定で渡す。本文をシェルのコードとして展開させない。

## 完了確認

PR の URL、base/head、送信されたコミットが意図どおりであることを確認する。
CI が実行された場合は状態を確認し、成功・失敗・実行中を区別して報告する。
CI の成功をローカル検証だけから推測しない。
