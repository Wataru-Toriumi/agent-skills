# Commit changes

ユーザーが指定した変更を、内容と検証結果が伝わるコミットとして残す。
メッセージ案だけの依頼なら、ステージやコミットは行わない。
利用先リポジトリの指示と既存のコミット規約を優先する。

## 対象を決める

- 現在のブランチ、作業ツリー、ステージ済み・未ステージ・未追跡の変更を確認する。ステージ済みでも、依頼の対象とは限らない。
- 差分と関連コードを読み、依頼された変更の範囲を特定する。対象が判断できない変更だけをユーザーに確認する。
- 無関係な変更を復元・削除したり、認証情報や生成キャッシュを混入させたりしない。既存のステージ状態も尊重する。
- 独立して説明・検証できる変更は分割する。一緒でなければ動かない実装とテストなどは同じコミットにまとめる。

## コミットする

1. 変更に必要な検証を実行する。既に実行済みで、その後に対象が変わっていない検証は再利用できる。実行できなかった検証や失敗は明示する。
2. ファイルまたは差分単位で対象をステージする。既存のステージ済み変更が混在する場合は、無関係な内容を含めず、そのステージ状態を保てる方法を選ぶ。
3. コミット直前にステージ差分全体を確認し、意図した変更だけが含まれることを確かめる。
4. リポジトリに規約がなければ Conventional Commits の `type(scope): summary` を使う。scope は有用な場合だけ付け、実際の変更理由を簡潔に表す。根拠のない issue 番号や共同著者を付けない。
5. 通常のフックを通してコミットする。フックがファイルを変更したら差分を読み、対象を再確認してからやり直す。原因が解消できない失敗は報告し、検証を迂回して続行しない。

履歴の書き換えや破壊的な操作（amend・reset・force push など）は、明示的に依頼された場合に限る。
push は依頼に含まれる場合、または依頼された PR 作成に必要な場合に行う。
既に許可された操作について、追加の確認を挟まない。

## 完了報告

コミットの短い SHA・件名、実施した検証、残った変更を簡潔に示す。
push した場合はその結果も示し、ローカルのコミット完了と区別する。
