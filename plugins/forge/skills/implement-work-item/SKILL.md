# 作業項目を実装する

要求・差分・検証結果を対応づけ、次の工程を再開できる状態で引き継ぐ。
設計だけ、レビューだけの依頼には、それぞれのスキルを使う。

## 入力と到達点を確かめる

- 作業ID、要求・設計、対象リポジトリ、開始コミット、受け入れ条件を読む。IDがなければ仮の識別名を付け、外部サービスのIDを作ったことにはしない。
- 変更範囲、許可された操作、対象外、必要なレビュー、到達点を依頼とリポジトリの指示から決める。実装依頼だけなら実装・検証まで。PRまでの依頼には必要なコミット・pushを含む。
- 未コミット・ステージ済み変更を確認し、別作業の変更を保持する。要求が衝突する、受け入れ条件が決まらない、必要な権限がない場合は、影響する工程を判断待ちにする。
- 記録は既存の課題や作業メモを優先する。指定がなければ会話で保持し、保存を求められた場合だけ [作業記録](assets/work-record.md) を使う。

## 実装・検証する

1. 受け入れ条件ごとに、確認方法と検証コマンドを定める。必要なら利用可能な `probe` の `plan-tests`、`design-tests`、`review-test-cases` を使う。未導入でも、要求・リスク・ケース・期待結果を整理して続ける。
2. 対象箇所と依存先を調べ、受け入れ条件を満たす変更を実装する。周辺の整理は変更に必要な範囲に絞り、別の改善を混ぜない。
3. 変更に合うテストとリポジトリ必須の検証を進める。成功・失敗・未実行を分け、コマンド、終了結果、対象リビジョン、ログの保存先を残す。検証対象はコミットSHA、未コミットなら開始SHAと差分を識別できる記録で示す。
4. [review-code](../review-code/SKILL.md) でセルフレビューし、必要なレビューを受ける。認証・権限、データ移行、公開APIの互換性など影響の大きい変更は、利用先の規約に沿って別セッションまたは人へ元の要求・差分・証跡を渡す。手配できなければレビュー待ちとして残す。
5. 指摘への修正後は、影響する検証とレビューを更新する。同じ失敗への再試行は既定で2回までとし、新しい根拠のない再実行を続けない。上限に達したら検証失敗にし、原因候補と次の手を示す。利用先の上限指定を優先する。

## 提出と完了

- コミットまでなら [commit-changes](../commit-changes/SKILL.md)、PRまでなら [create-pr](../create-pr/SKILL.md) に引き継ぐ。既に行ったレビュー・検証は、対象差分が同一なら再利用し、作業だけを重複させない。
- コミット後は、検証した差分が対象SHAの内容と一致することを確認する。PRではそのheadを対象とするCI・レビューを確認し、実行中や古いheadへの成功を完了扱いしない。
- 完了は、対象コミットの受け入れ条件と必須検証が成立し、必要なレビューと依頼された提出が終わった場合だけ。実装・検証までの依頼でコミットしていない場合は、実装済みとして次の工程へ引き継ぎ、作業全体の完了とは分ける。
- マージ・公開・本番操作は、この手順を選んだことだけでは許可されたと扱わない。

## 状態と再開

状態は未着手・実行中・判断待ち・検証失敗・完了を使う。判断待ちには判断事項と担当、検証失敗には失敗した条件を添える。
中断時は最新SHA、未コミット差分、実施済み工程、未解決事項、次の工程、再試行回数を記録する。
再開時は現在の作業ツリーと記録を照合し、差分・要求・実行環境が変わった範囲の検証をやり直す。
外部操作の応答が不明な場合は、リモートの状態を照合してから再試行し、成功を推測して二重送信しない。
