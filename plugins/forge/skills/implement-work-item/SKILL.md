# 作業項目を実装する

どの要求をどの差分で満たしたかを検証結果とともに記録し、次の工程を再開できるように引き継ぐ。
設計だけ、レビューだけの依頼には、それぞれのスキルを使う。

## 入力と到達点を確かめる

- 作業 ID、要求・設計、対象リポジトリ、開始コミット、受け入れ条件を確認する。ID がなければ仮の名前を付け、外部サービスが発行した ID と区別する。
- ink の作業項目や pulse の改善策を受け取る場合は、元の問題・根拠・採用した変更と受け入れ条件を照合する。条件が揃っていれば整理工程を繰り返さず、挙動や範囲を左右する未決事項だけを要求整理へ戻す。必要なら利用可能な ink の `clarify-requirements`、`write-work-item` を使う。
- 運用改善では、適用後の効果指標・比較元・観測期間・悪影響や見直しの条件を引き継ぎ、実装の受け入れ条件と分ける。測定値が不足していても、独立して実装できる範囲は進め、効果は未確認として残す。
- 変更範囲、許可された操作、対象外、必要なレビュー、到達点を依頼とリポジトリの指示から決める。実装依頼だけなら実装・検証まで。PRまでの依頼には必要なコミット・pushを含む。
- 未コミット・ステージ済み変更を確認し、別作業の変更を保持する。要求が衝突する、受け入れ条件が決まらない、必要な権限がない場合は、影響する工程を判断待ちにする。
- 記録は既存の課題や作業メモを優先する。指定がなければ会話で保持し、保存を求められた場合だけ [作業記録](assets/work-record.md) を使う。

## 実装・検証する

利用経路・成功や失敗の判定・指標やログが変わる場合は、[pulse への引き継ぎ](references/monitoring-handoff.md)で監視と初動への影響を確認する。設計時の監視案を実際の差分と照合し、依頼範囲で必要な実装・検証へ反映する。

probe の指摘に対する修正では、対象版・要求・期待結果・再現条件・証跡を照合し、現行コードで不一致が成立するか確認する。モデルやテスト自体の不備、未決の仕様、タイムアウトをコードの欠陥と扱わない。
修正後は対象版・差分・影響する回帰検証の結果を元の指摘へ返し、要求変更があればその理由と合意を示す。反例を検出するテストの期待結果を、修正後の実装に合わせるだけで変更しない。

1. 受け入れ条件ごとに、確認方法と検証コマンドを定める。必要なら利用可能な `probe` の `plan-tests`、`design-tests`、`review-test-cases` を使う。未導入でも、要求・リスク・ケース・期待結果を整理して続ける。
2. 対象箇所と依存先を調べ、受け入れ条件を満たす変更を実装する。周辺の整理は変更に必要な範囲に絞り、別の改善を混ぜない。
3. 変更に合うテストとリポジトリ必須の検証を進める。成功・失敗・未実行を分け、コマンド、終了結果、対象リビジョン、ログの保存先を残す。検証対象はコミットSHA、未コミットなら開始SHAと差分を識別できる記録で示す。
4. [review-code](../review-code/SKILL.md) でセルフレビューし、必要なレビューを受ける。認証・権限、データ移行、公開APIの互換性など影響の大きい変更は、利用先の規約に沿って別セッションまたは人へ元の要求・差分・証跡を渡す。手配できなければレビュー待ちとして残す。
5. 指摘への修正後は、影響する検証とレビューを更新する。同じ失敗への再試行は既定で2回までとし、新しい根拠のない再実行を続けない。上限に達したら検証失敗にし、原因候補と次の手を示す。利用先の上限指定を優先する。

## 提出と完了

説明の推敲・図解が必要な場合や、発表資料・HTML の説明ページを求められた場合は、[sketch との連携](../create-pr/references/sketch-collaboration.md)に従い、利用可能なスキルで整えて元の内容と照合する。

- コミットまでなら [commit-changes](../commit-changes/SKILL.md)、PRまでなら [create-pr](../create-pr/SKILL.md) に引き継ぐ。対象の差分が同じなら、レビュー・検証の結果を再利用する。
- コミット後は、検証した差分が対象SHAの内容と一致することを確認する。PRではそのheadを対象とするCI・レビューを確認し、実行中や古いheadへの成功を完了扱いしない。
- 完了は依頼された到達点で判定する。実装・検証までなら、受け入れ条件・必須検証・必要なレビューを満たし、検証した作業ツリーを開始 SHA と差分（新規ファイルを含む）で特定できれば完了とする。最終検証後に対象が変わった場合は、その影響範囲を再確認する。
- コミットや PR までの依頼は、その提出と対象版の確認までを完了条件に含める。
- マージ・公開・本番操作は、この手順を選んだことだけでは許可されたと扱わない。

## 運用改善の結果を返す

運用改善を実装した場合は、元の改善策に対象SHA・差分・受け入れ条件ごとの検証結果、残るリスク、実際の適用状況を対応付けて返す。
実装済み・適用済み・効果確認済みを分け、PR作成やテスト成功だけで改善全体を完了としない。
適用後の評価も依頼に含まれ、観測データがあれば、利用可能な pulse の `improve-operations` に効果の測定条件と結果を渡す。
未適用・観測不足なら次の確認に必要なデータ・時期・担当を残し、効果の確認待ちとする。未定の担当や時期を補わない。pulse が利用できなくても同じ情報を返せる。

## 状態と再開

状態は未着手・実行中・判断待ち・検証失敗・完了から選ぶ。判断待ちには判断事項と担当を、検証失敗には失敗した条件を添える。

- 中断時は最新 SHA、未コミットの差分、実施済みの工程、未解決事項、次の工程、再試行回数を記録する。
- 再開時は作業ツリーと記録を照合する。差分・要求・実行環境が変わった範囲は再検証する。
- 外部操作の結果が不明なら、二重送信を防ぐため、再試行の前にリモートの状態を照合する。
