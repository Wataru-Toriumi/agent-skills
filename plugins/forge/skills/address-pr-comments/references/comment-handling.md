# コメントの扱いと対応例

## コメントと返信先

GitHub の一般コメント、レビュー本文、差分へのコメントは別の情報として取得されることがある。
利用可能な GitHub 接続ツールや CLI で対象を確認し、取得機能がどこまでを含むか調べる。

| 種類 | 確認すること | 返信先 |
| --- | --- | --- |
| 一般コメント | PR 全体の質問・要望と後続の議論 | PR の会話。元コメントへの参照を添える |
| レビュー本文 | 総評に含まれる指摘と、そのレビューの個別コメント | 該当する個別スレッド、またはレビューを参照した PR の会話 |
| 行・ファイルへのコメント | 指摘時点の差分、返信、現在のコード、スレッド状態 | 元のレビュースレッド |

REST API を使う場合、一般コメントは issue comments、差分へのコメントは pull request review comments として扱う。
スレッドの解決状態が取得結果に含まれなければ、状態を取得できる別の機能を使うか未確認とする。
返信 ID とスレッド ID を混同せず、利用する API が要求する宛先を確かめる。

## 判断と返信の例

架空の例。コミットやテスト結果は、実際に確認したものへ置き換える。

| 状況 | 対応 | 返信に残す要点 |
| --- | --- | --- |
| 「空の配列で失敗する」が再現した | 空の場合の扱いを修正し、回帰を検証する | 何を修正したか、検証結果、PR 反映済みならコミット |
| 「権限チェックがない」とあるが、呼び出し元で検査している | 問題となる入口でも検査されるか追う | 該当コードと適用条件。別の入口の指摘なら、その条件を確認する |
| 古い差分に「二重送信される」とある | 現行コードでも起きるか確認する | 解消済みなら変更の根拠。残っていれば修正方針 |
| 同じ指摘に既に回答し、新しい反論はない | 再投稿せず、残る修正や確認だけを進める | 対応報告では既存の返信を参照する |
| 「同期にする」「非同期を維持する」が並んでいる | 守りたい要件と影響を整理し、判断を求める | 争点、選択肢、確認先。両方に対応済みとは答えない |
| 別機能の追加を求められた | 今回の範囲との違いと切り出し案を示す | 保留理由と次の扱い。Issue 未作成なら作成済みとしない |

短い返信例:

> 空の場合は処理を終了するよう修正しました。空配列と通常入力のテストは成功しています。修正はまだローカルのみです。

解決済み表示は、レビュー者の承認や CI の成功を意味しない。コードの修正状況、返信の送信状況、スレッドの状態を別々に確認する。
