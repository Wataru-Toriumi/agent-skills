# Mermaid で伝わる図を描く

読者が図から判断したいことを一つ定め、必要な関係を読み取れる図にする。
ユーザーが指定した形式・図種・表記と、利用先の慣例を優先する。

## 目的と出力先を揃える

- 図の目的、読者、根拠となる資料・コード、掲載先を確認する。入力から分かることは聞き直さない。未決の関係や条件は、図の注記または近くの本文に残す。
- 既存図の修正では、その意味・要素 ID・参照関係を保ち、依頼された変更と可読性に関わる箇所を直す。見栄えのために権限判定・失敗経路・重要な境界を消さない。
- チャットや Markdown 文書には `mermaid` コードブロック、独立したソースには `.mmd` を使う。画像が必要なら SVG / PNG も生成し、編集できるソースを残す。チャットの草案依頼で永続ファイルを増やさない。
- 他のプラグインから利用される場合は、[受け取りと返却の手順](../polish-writing/references/plugin-collaboration.md)に従い、図の目的・粒度・配色の指定も引き継ぐ。

## 図種と粒度を選ぶ

[図種の選び方](references/diagram-types.md)から、構造・振る舞い、要求・利用体験、計画・比較の目的に合う図種を選ぶ。選んだ図種の例だけを読み、掲載先の対応を確認する。
例にない図種を使う場合は、[公式の図種一覧](https://mermaid.js.org/intro/)で構文と対応条件を確認する。図種の指定がなく、文章や表の方が明快なら図を増やさない。
構成図と処理順序、業務全体と関数内部など、異なる問いや粒度を一枚に詰め込まない。
C4 の粒度を表したい場合も、Mermaid の専用 C4 構文を必須にせず、掲載先が対応する記法を選ぶ。

## 読みやすく組み立てる

- 主経路を先に置き、読む方向を揃える。流れが横に伸びるなら `LR`、縦に追う方が自然なら `TD` を起点に、実際の掲載幅で調整する。
- ラベルは短い役割名・状態名・動作にする。長い理由や注釈は図の近くへ移し、本文と図の用語を揃える。接続が複数の意味を持つ場合は矢印に動詞を付ける。
- 機能名を並べるだけで終わらず、説明したい経路・受け渡すもの・条件を示す。変更前後や複数案は用語・方向・粒度を揃え、変わる部分を強調する。比較時の配置は [表現とデザイン](../explain-visually/references/visual-design.md) を参照する。
- ノード・矢印・グループのラベルは、[改行と折り返し](references/rendering.md#ラベルの改行と折り返し)に沿って意味のまとまりを保つ。図単体と最終的な掲載先の両方で確認する。
- グループはシステム境界や責務を表すために使う。線が交差して追えない場合は、まず要素順・方向・グループを調整し、それでも難しければ概要と詳細に分ける。文字を小さくして押し込まない。
- [配色ルール](references/colors.md)を使い、指定色や掲載先の配色を優先する。指定がなければ通常ノード・境界・接続線はグレーを基調にする。処理フローでは判断・引き継ぎ・完了など、読み分けたい役割に淡いアクセント色を割り当て、同じ役割には同じ色を使う。差分図では既存・変更・未決の色分けを使う。どちらもラベルや形で意味を読めるようにする。
- 処理結果を示すときは警告にアンバー、失敗に赤を使い、ラベルに状態とその後の動作を示す。
- 掲載先の明暗とテーマ設定の対応を確認する。色を固定した図が明暗へ自動追従するとは考えない。アイコン・追加レイアウトも対応を確認して選ぶ。
- 図が何を示し、どの条件でどんな結論を読み取れるかを短く添える。要素の一覧は本文で繰り返さない。根拠のないコンポーネント、順序、多重度、例外時の処理を補って確定情報にしない。

## 動的な表現を選ぶ

- 動きで伝えたいことと掲載先を確認し、流れの強調、順番の再生、クリック操作、データによる更新を区別する。静止図で伝わる場合は動きを増やさない。
- 動的表現が必要なら [動的表現の選択と検証](references/dynamic.md) を読む。Mermaid の対応バージョンと、掲載先が許可する機能の範囲で選ぶ。図の依頼だけで掲載先の設定を変更しない。
- 矢印・ラベル・番号で意味を残し、動きやクリックがなくても要点を読めるようにする。対応が不明な場合は静止版を渡し、希望する動作と未確認事項を添える。

## 描画して見直す

1. 利用先のプレビュー、利用可能なローカルのレンダラーなどで描画する。実行方法や互換性の確認には [描画と検証](references/rendering.md) を使う。
2. 生成画像またはプレビューを開き、文字の欠け、ラベルの重なり、線の交差、横幅、色の判別、読み順を確認する。構文解析の成功だけで見た目も確認済みにしない。
   アニメーションや操作はブラウザーで実際に試す。静止画像だけを確認した場合は、動作は未検証とする。
3. 問題があれば図を修正して再描画する。環境不足で描画できない場合は、ソースと未検証の範囲を渡す。同じ環境エラーを繰り返したり、図の依頼だけで利用先の設定を変更したりしない。
4. 図と元資料で要素・条件・境界が一致するか見直す。最終的に使ったレンダラーと確認範囲を簡潔に伝え、ローカルでの成功を GitHub など掲載先での成功と同一視しない。
