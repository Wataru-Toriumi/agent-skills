# Mermaid で伝わる図を描く

読者が図から判断したいことを一つ定め、必要な関係を読み取れる図にする。
ユーザーが指定した形式・図種・表記と、利用先の慣例を優先する。

## 目的と出力先を揃える

- 図の目的、読者、根拠となる資料・コード、掲載先を確認する。入力から分かることは聞き直さない。未決の関係や条件は、図の注記または近くの本文に残す。
- 既存図の修正では、その意味・要素 ID・参照関係を保ち、依頼された変更と可読性に関わる箇所を直す。見栄えのために権限判定・失敗経路・重要な境界を消さない。
- チャットや Markdown 文書には `mermaid` コードブロック、独立したソースには `.mmd` を使う。画像が必要なら SVG / PNG も生成し、編集できるソースを残す。チャットの草案依頼で永続ファイルを増やさない。
- `ink` などから利用される場合は、渡された目的・粒度・確定事項・配色の指定を引き継ぎ、図のソース、短い説明、検証状況を返す。要求や設計判断の採否を作図側で決めない。

## 図種と粒度を選ぶ

| 説明したいこと | 第一候補 | 残す情報 |
| --- | --- | --- |
| 構成要素の責務・境界・依存 | [flowchart](examples/flowchart.md) | 要素の役割、境界、接続の意味 |
| 操作や判断の分岐 | [flowchart](examples/flowchart.md) | 起点、条件、分岐先、結果 |
| 複数主体の呼び出し順・応答 | [sequenceDiagram](examples/sequence.md) | 参加者、メッセージ、重要な成功・失敗の分岐 |
| 一つの対象の状態と変化 | [stateDiagram-v2](examples/state.md) | 状態、遷移の契機・条件、終了条件 |
| データ同士の関連 | [erDiagram](examples/er.md) | エンティティ、関連、多重度、必要なキー |

これは標準候補であり、他の図種を制限しない。図種の指定がなく、文章や表の方が明快なら図を増やさない。
構成図と処理順序、業務全体と関数内部など、異なる問いや粒度を一枚に詰め込まない。
C4 の粒度を表したい場合も、Mermaid の専用 C4 構文を必須にせず、掲載先が対応する記法を選ぶ。
図種ごとの注意点や最小例が必要なら、表のリンクから選んだ図種の例だけを読む。

## 読みやすく組み立てる

- 主経路を先に置き、読む方向を揃える。流れが横に伸びるなら `LR`、縦に追う方が自然なら `TD` を起点に、実際の掲載幅で調整する。
- ラベルは短い役割名・状態名・動作にする。長い理由や注釈は図の近くへ移し、本文と図の用語を揃える。接続が複数の意味を持つ場合は矢印に動詞を付ける。
- グループはシステム境界や責務を表すために使う。線が交差して追えない場合は、まず要素順・方向・グループを調整し、それでも難しければ概要と詳細に分ける。文字を小さくして押し込まない。
- 配色を決めるときは [配色ルール](references/colors.md) を読み、ユーザー指定、利用先の既存配色、sketch の標準パレットの順に優先する。標準は通常・既存をグレー、変更・提案を青、未決・要確認をアンバーにする。必要な強調だけを使い、ラベルや線種でも意味を示す。
- 掲載先の明暗とテーマ設定の対応を確認する。色を固定した図が明暗へ自動追従するとは考えない。アイコン・追加レイアウトも対応を確認して選ぶ。
- 図の対象と読み取る結論を短く添える。根拠のないコンポーネント、順序、多重度、例外時の処理を補って確定情報にしない。

## 描画して見直す

1. 利用先のプレビュー、利用可能なローカルのレンダラーなどで描画する。実行方法や互換性の確認には [描画と検証](references/rendering.md) を使う。
2. 生成画像またはプレビューを開き、文字の欠け、ラベルの重なり、線の交差、横幅、色の判別、読み順を確認する。構文解析の成功だけで見た目も確認済みにしない。
3. 問題があれば図を修正して再描画する。環境不足で描画できない場合は、ソースと未検証の範囲を渡す。同じ環境エラーを繰り返したり、図の依頼だけで利用先の設定を変更したりしない。
4. 図と元資料で要素・条件・境界が一致するか見直す。最終的に使ったレンダラーと確認範囲を簡潔に伝え、ローカルでの成功を GitHub など掲載先での成功と同一視しない。
