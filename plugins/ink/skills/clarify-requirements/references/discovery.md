# 深掘りの観点と例

## 次の質問を選ぶ

全項目を順に聞く質問票として使わず、今回の判断に影響する不足から選ぶ。
まず実際に起きたことを聞き、案の比較は課題と制約が分かってから行う。選択肢を示す場合も、別の答えや「まだ分からない」を選べるようにする。

| 不明なこと | 質問の例 | 明らかにすること |
| --- | --- | --- |
| 対象者と状況 | 直近で困った場面では、誰が何をしようとしていましたか | 主体・きっかけ・達成したいこと |
| 現状の障害 | 今はどう対処し、どこで作業が止まっていますか | 現在の流れ・回避策・障害 |
| 影響 | その場面はどの程度起き、誰にどんな影響がありますか | 頻度・負担・優先度の根拠 |
| 期待する成果 | 何が変われば、困りごとが解消したと判断できますか | 成果・観測方法 |
| 範囲 | 今回必ず扱う場面と、後に回せる場面はどれですか | 対象・対象外・段階的な提供 |
| 境界と例外 | その条件を満たさない場合、どう扱う必要がありますか | 適用範囲・期待結果・未決のルール |
| 制約 | その条件が必要な根拠や、変更できない理由は何ですか | 必須制約と希望の区別 |
| 品質条件 | どの利用条件で、どの程度の待ち時間や停止が業務に影響しますか | 性能・可用性などの要求と測定条件 |
| 衝突 | それぞれの要望が守ろうとしていることと、判断できる人は誰ですか | 対立の背景・判断者・確認先 |

「通知を増やせば解決しますか」のように解決策へ誘導せず、まず「見落とした直近の場面では、どこで申請を確認していましたか」と状況を確かめる。
仮説を提示する場合は仮説と明示し、反例や違う事情も聞く。要望が「通知を追加する」と決まっていても、通知手段・頻度まで確定したとは扱わない。

## Example Mapping で振る舞いを具体化する

[Cucumber の Example Mapping](https://cucumber.io/docs/bdd/example-mapping/) を参考に、対象の要求・ルール・具体例・未決の問いを対応付ける。
まだ具体的な振る舞いが見えていない段階では、先に対象者と課題を確かめる。

| 要素 | 内容 |
| --- | --- |
| 対象 | 今回明らかにする要求や振る舞い |
| ルール | 期待する振る舞いや制約。出所と合意状況を添える |
| 具体例 | 状況・操作や出来事・観測できる結果。実際の経験と確認用の仮例を区別する |
| 問い | 結果や適用範囲を決められない点。確認先・方法を添える |

たとえば「承認待ちの申請は取り消せる」が合意済みなら、「申請者が承認待ちの申請を取り消すと、取消済みになる」は確認用の仮例になる。
承認後も取り消せるか不明なら、その扱いは問いに残す。この例から、承認後の取消機能や管理者権限を新しい要求として追加しない。

例を説明できない原因が情報不足なら、資料確認や関係者への確認につなぐ。意見の多数決で期待結果を埋めない。
この段階では自然文でよく、Gherkin やテストコードへの変換は求めない。
