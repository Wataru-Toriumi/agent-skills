# ADR を作成・更新する

一つの重要な設計判断について、その時点の状況と選択理由を後から追えるように記録する。

## 文脈と保存先

- ユーザーの説明、関連する Design Doc、既存 ADR、必要なコードを確認する。現在の実装だけから、当時の判断理由を推測して事実にしない。
- 文書の言語、書式、状態名、番号付けはユーザーの指定とリポジトリの慣例に合わせる。慣例がなければ `docs/adr/<連番4桁>-<topic>.md` を使い、既存の番号を確認して次の番号を選ぶ。最初は `0001` とする。チャット上の草案を求められた場合はファイルを作らない。
- 同じ判断を扱う ADR がある場合は先に読み、新規作成、既存草案の更新、既存判断の置き換えのどれに当たるか整理する。

## 判断を記録する

1. 決定内容を最初に一文で示す。ユーザーや資料が採用済みと明示していれば、その決定を記録する。採用の根拠がなければ Proposed の草案とし、Accepted にしない。独立した判断は別の ADR に分ける必要があるか検討する。
2. 判断時の課題・制約と、それに対してこの案を選ぶ理由をつなげて説明する。期待する効果もここに含め、背景と理由で同じ説明を繰り返さない。
3. 受け入れる不利益、運用負担、制約と必要な対応を記す。未確認の不利益を「なし」と断定したり、一般的な欠点で埋めたりしない。

新規文書は [ADR テンプレート](assets/adr-template.md) の「決定・背景と理由・受け入れる不利益」を基本とする。既存書式がある場合はそちらを優先する。

## 説明を追加する条件

- 選択肢の構成や判断の影響を Mermaid で図示する場合は、利用可能な `sketch` プラグインの `draw-mermaid` スキルを適用する。目的・読者・比較対象と確定状況・掲載先を渡し、図が判断と一致するか確認する。利用できなくても文書作成を続け、未検証の描画を確認済みとしない。
- 他案との違いが選択理由を左右する場合は、その違いを記す。複数の案と基準を比べる必要があるときだけ比較表を使う。実際に検討した根拠のない案は「追加の比較候補」として区別する。
- 判断が特定の前提に依存する場合は、見直す条件を添える。判断を妨げる未決事項には、その影響と確認方法を示す。
- 判断日・決定者・関連資料は、確認できる情報や既存書式で必要な情報を添える。記載が必要でも不明なら未確認とし、現在の日付や文書作成者で埋めない。置き換え時の ADR 相互参照は必ず残す。

## 既存 ADR の扱い

- Proposed の文書は、議論の進展に合わせて内容と状態を更新する。
- Accepted の判断を変更する場合は、原則として新しい ADR に置き換える理由を記録し、旧 ADR と相互に参照する。旧 ADR の本文を新しい判断に書き換えて履歴を消さない。
- 新しい案がまだ提案段階なら、旧 ADR を Superseded にしない。置き換えが確定した場合に、既存の状態名の規約に従って旧 ADR の状態と参照先を更新する。
- 誤字の修正や参照切れの修正では、判断の意味を変えず必要な箇所を直す。

## 仕上げ

- 判断に必要な最小限の文章にする。一般論、作業の時系列、他文書の転記を省き、根拠は該当箇所からリンクする。空の節や無関係な項目は作らない。文字数を減らすために重要な理由・不利益・未決事項を落とさない。
- 状況から選択理由、決定、結果までがつながり、提案と確定済みの判断が区別されているか確認する。
- 番号・リンク・置き換え関係に矛盾がないか確認する。既存の索引があれば、その運用に合わせて更新する。
- 作成・更新した文書の場所、記録した判断、未確定の点を短く伝える。
