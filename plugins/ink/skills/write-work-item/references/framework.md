# 整理と分割の基準

## 階層の使い分け

イニシアチブ・エピック・ストーリーは、成果から具体的な提供単位へつなぐための既定の整理方法とする。
階層や粒度は組織によって異なるため、期間や項目数だけで分類しない。
この関係の参考は [Atlassian: Epics, Stories, and Initiatives](https://www.atlassian.com/agile/project-management/epics-stories-themes/) を参照する。

- **イニシアチブ:** 現状の問題、目指す変化、測定方法をつなぐ。機能のリリース数だけで成果を判断しない。基準値・目標値・評価時期に根拠がなければ未決とし、測定の提案と区別する。
- **エピック:** 一貫した能力・体験の提供範囲を示す。ストーリー一覧だけでなく、全体として何ができれば完了かを記す。
- **ストーリー:** 「〈利用者〉として、〈達成したいこと〉をしたい。〈得られる価値〉のために」を基本にする。状況が重要なら「〈状況〉のとき、〈達成したいこと〉をしたい。それによって〈期待する成果〉を得たい」という Job Story を使う。両方の形式を重複して書かない。

## INVEST でストーリーを点検する

[Bill Wake の INVEST](https://xp123.com/invest-in-good-stories-and-smart-tasks/) を、説明の不足や分割候補を見つける観点として使う。
採点表の出力や全項目の形式的な合格は求めない。

| 観点 | 確認すること |
| --- | --- |
| Independent | 他のストーリーとの結合を減らせるか。残る依存は何か |
| Negotiable | 必須の制約と、実現時に相談できる詳細を分けているか |
| Valuable | 誰にどんな価値があるか。実装部品の完成だけになっていないか |
| Estimable | チームが見積もるための範囲と不確実性が分かるか |
| Small | 実装だけでなく、テスト・必要なレビューまで含めて分割目安に収まるか |
| Testable | 条件と観測できる期待結果から合否を判断できるか |

見積もれる説明にすることと、見積もり値を代わりに決めることは別とする。
不確実性が大きく所要日数を判断できなければ、先に調査する項目とその終了条件を示す。
日数に収めるために価値や受け入れ条件を削らず、分割が難しい場合は理由と残る依存を記す。

## 分割と受け入れ条件

- 振る舞い・業務ルール・対象範囲の違いで、価値を保って小さくする。例として「申請する」を、まず通常の申請、次に代理申請へ分ける案がある。代理申請は入力の要求に含まれる場合だけ扱う。
- 「申請画面」「申請 API」「申請テーブル」は技術的な作業分解であり、それぞれを利用者向けのストーリーとして扱わない。
- 受け入れ条件は、たとえば「申請権限を持つ利用者が必須項目を入力して送信すると、申請が保存され、受付番号が表示される」のように観測可能にする。保存や受付番号が要求にない場合は追加しない。
- 権限・例外・非機能条件は今回の範囲に関係するものを記す。合意されていない振る舞いは提案または未決として分ける。
- 分割した子の条件で親の範囲を満たせるかを確認する。親にある必須条件を分割の都合で落とさず、子の完了だけでは測れない成果は別途評価する。
