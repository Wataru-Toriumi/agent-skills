# イニシアチブ・エピック・ストーリーを作成・更新する

「なぜ取り組むか」「何を提供するか」「何をもって受け入れるか」を、対象の粒度に合わせて短く記す。
PRD は要求の根拠として参照し、このスキルでは実行・追跡する単位の説明を整える。

## 対象と文脈を確認する

- 対象の説明、関連する親子項目、PRD や調査メモを読む。既存の階層・用語・書式を優先し、3階層を必須にしない。単一ストーリーの依頼から上位項目まで新設しない。
- 新規作成・更新・分割のどれを求められているか確認する。粒度が曖昧なら、成果を追う単位か、提供範囲を束ねる単位か、一つの振る舞いを届ける単位かで判断する。
- 対象者・目的・範囲が変わる不足だけを質問し、他は未決として草案を進める。提案と合意済みの内容を区別し、根拠のない目標値・期限・担当者・見積もりを補わない。
- 保存先はユーザーの指定と既存の慣例を優先する。ファイル作成で慣例がなければ `docs/work-items/<type>/<topic>.md`（`type` は `initiatives`・`epics`・`stories`）とする。会話やチケット本文の草案ならファイルを作らず、外部への登録・更新は依頼に含まれる場合に行う。

## タイトルを付ける

一覧でも対象と変化が読み取れるタイトルにする。既存の命名規則を優先し、指定がなければ次の型を使う。

| 種類 | タイトルの型 | 例 |
| --- | --- | --- |
| イニシアチブ | 〈対象〉の〈課題・成果指標〉を〈改善する〉 | 経費精算にかかる時間を短縮する |
| エピック | 〈業務・体験〉を〈実現できる状態〉にする | 経費申請から承認までオンラインで完結できるようにする |
| ストーリー | 〈利用者〉が〈具体的な行動〉できる | 申請者が領収書を添付して経費を申請できる |

- 「経費精算改善」「申請対応」のような対象名と曖昧な動詞だけで終えず、何がどう変わるかを示す。
- 一つの成果・提供範囲・振る舞いを中心に書く。ストーリーに独立した行動を列挙する場合は、1〜2日の分割目安と個別の受け入れ可否を確認する。
- 本文のスコープ・受け入れ条件と一致させる。「すべて」「自動化」などで実際の提供範囲を広げない。背景や詳細な条件は本文に置く。

## 粒度に合わせて書く

| 種類 | 説明の中心 | ひな形 |
| --- | --- | --- |
| イニシアチブ | 課題と期待する成果、対象範囲、成果の測定方法、関連エピック | [initiative-template.md](assets/initiative-template.md) |
| エピック | 誰にどんな能力・体験を届けるか、対象と対象外、完了条件、関連ストーリー | [epic-template.md](assets/epic-template.md) |
| ストーリー | 利用者と状況、達成したいことと価値、受け入れ条件 | [story-template.md](assets/story-template.md) |

1. **目的と範囲:** 本文には背景の要点を置き、PRD の要求 ID や根拠をリンクする。背景・制約の全文を各階層に複製しない。
2. **確認方法:** イニシアチブは成果を何で・いつ観測するかを示す。エピックは提供範囲全体の完了条件を、ストーリーは Given / When / Then に相当する前提・操作や出来事・観測できる結果を記す。子項目の完了と、事業・利用者の成果達成を区別する。
3. **親子のつながり:** 親のどの成果・範囲を支えるかを一文で示し、実在する ID・リンクでつなぐ。未作成の子項目は候補と明記する。依存先は親子関係と分け、何を待つかを書く。
4. **分割:** ストーリーは実装・テスト・必要なレビューを含め、原則1〜2日程度で完了できる粒度を目安にする。超える場合は、利用者が価値を確認でき、個別に受け入れられる振る舞いで分割を検討する。画面・API・DB だけの分割は実装タスクとして区別し、分割後に元の範囲の抜け・重複を確認する。ユーザーやチームが別の粒度を指定している場合はそちらを優先する。

ストーリーは INVEST を使って粒度と説明を点検する。詳細は [整理と分割の基準](references/framework.md) を参照する。
技術作業や調査は目的・成果物・終了条件で説明し、架空の利用者を置いてストーリーに変換しない。

## 技術詳細を絞る

- 本文は「何を実現するか」を中心に書く。コンポーネント名や技術的制約は、その記述がないとスコープ・依存関係・受け入れ可否を判断できないものに絞る。
- クラス構成、内部 API、DB スキーマ、内部の処理手順などの設計詳細は、関連する Design Doc をリンクして参照し、本文に複製しない。
- 技術用語だけで除外しない。たとえば連携先 API の互換性が必須条件なら残し、内部クラスの呼び出し順は設計文書で扱う。合意済みの制約は要点と根拠を保持する。

## 既存の説明を更新する

- ID・参照先・合意済みの制約を保持する。説明の更新に伴って、ステータス・担当者・優先度などを勝手に変更しない。
- 変更理由を根拠に、目的・範囲・受け入れ条件の対応を揃える。親の制約との衝突や子項目への影響を確認する。
- 関連項目の変更が必要でも依頼範囲外なら、対象と修正案を示す。未確認の変更を合意済みとして反映せず、過去の決定を黙って上書きしない。
- 分割・統合では元の項目との対応を残し、参照切れを防ぐ。作業の完了実績がなければ、説明が整っただけで完了扱いにしない。

## 仕上げ

- 各項目だけでも目的・範囲・確認方法が分かり、親の範囲を逸脱していないか確認する。参照できなかった資料は未確認とする。
- 同じ背景の繰り返し、不要な節、テンプレートの案内を削る。判断を妨げる未決事項は確認先や確認方法とともに残す。
- 作成・更新した対象と、関連項目への影響、残る主要な判断を短く伝える。
