# Job Story から受け入れ条件までの整理例

入力を要求へ落とすときに迷った場合の参考。題材・機能・数値を実際の PRD へ流用しない。

## 例: 申請の進捗確認

架空の入力: 申請者は進捗が分からず承認担当へ個別に問い合わせている。今回は進捗を確認できるようにしたい。通知は対象外。

- 対象者: 申請後の次の行動を判断したい申請者。
- J-001: 申請後に手続きが進んでいないとき、現在の進捗と自分に必要な対応を把握したい。それによって、問い合わせを待たずに次の行動を判断したい。
- 現状の障害: 担当者の返答が来るまで状況を判断できない。これは入力から整理した仮説で、実際の利用者調査で確認済みとは扱わない。

「進捗画面を開きたい」は特定の解決策に寄っている。Job では、その操作で何を達成したいのかを書く。

以下の要求と条件も、入力をもとにした提案であり、合意済みの仕様ではない。

| ID | 対応する Job・制約 | 要求 | 受け入れ条件 |
| --- | --- | --- | --- |
| R-001 | J-001 | 申請者が現在の進捗を確認できる | 自分の申請が承認待ちである前提で、進捗を確認したとき、承認待ちであることが分かる。 |
| R-002 | J-001 | 申請者が次に必要な対応を確認できる | 自分の申請が差し戻され、修正事項が指定されている前提で、申請を確認したとき、対応すべき修正事項が分かる。 |

この例では自動通知を対象外とする。権限や他人の申請の可視性など、提示されていない重要な条件は必要に応じて確認する。
Job が複数あるときは必要なものだけ追加し、一つの要求が複数の Job に対応してもよい。

## 完成と成果を分ける

- 完成の確認: R-001・R-002 の受け入れ条件を満たすこと。
- 成果の確認: 申請者が個別問い合わせなしで次の行動を判断できるか、利用者への確認などで評価する。問い合わせ件数を指標にする場合は、測定期間・申請件数との関係・目標値を別途決める。

「問い合わせが減る」は価値の仮説であり、画面の受け入れ条件が通っただけでは実証されない。

## 使っている考え方

- [Intercom: Job Stories](https://www.intercom.com/blog/accidentally-invented-job-stories): 状況・動機・期待する成果で利用者の課題を整理する。
- [Cucumber: Given / When / Then](https://cucumber.io/docs/gherkin/reference/): 前提・出来事・観測できる結果で振る舞いを具体化する。

このスキルでは両者を PRD 用に組み合わせる。特定の PRD 標準への準拠や、JTBD の調査を実施済みであることは意味しない。
