# 設計レビューの例

以下は仮想の注文 API に対する例。要求・挙動・節名はこの例の入力であり、他のレビューで前提にしない。

## 入力

- 要求 R1: 応答を受け取れず同じ注文を再送しても、注文は一件だけ保存される。
- 設計「注文作成」: リクエストを受けるたびに注文 ID を新規発行し、保存を確定してから応答する。再送でも同じ処理を行う。
- 設計「閲覧」: 利用者を認証して注文を返す。注文の所有者と利用者の照合については記載がない。
- 設計「性能」: 想定ピークで応答時間の要求 R2 を満たす方針。具体的な負荷と応答時間は R2 に記載済みだが、計測結果はまだない。

## 利用側からの机上での追跡

呼び出し側は `createOrder(payload)` の応答を受け取れないと、同じ入力で再試行するものとする。
これは例のための擬似コードであり、実行結果ではない。

| 操作・出来事 | 保存済みの注文 | 呼び出し側が知っていること |
| --- | --- | --- |
| 初期状態 | なし | 未送信 |
| 注文を送信し、サーバーが保存 | A | 応答待ち |
| 応答が失われる | A | 保存されたか不明 |
| 同じ注文を再送し、サーバーが保存 | A、B | 二回目の応答待ち |

この経路で R1 違反を説明できる。仮に修正案に重複防止キーが追加された場合は、利用側が再送時にも同じキーを渡せるかをまず確認する。
同じキーの同時処理で「未登録の確認 → 保存」が競合しうるなら、二つのリクエストの状態と保存境界をモデル化して探索する候補になる。
この例ではモデル実行まで行ったとは扱わない。

## 出力例

### 重要な指摘

**採用・実装前に解消：応答喪失後の再送で注文が重複する**

対象は設計「注文作成」と要求 R1。保存確定後に応答が失われると、再送で別 ID の注文を保存する経路になり、R1 を満たせない。
同じ操作を識別し、並行した再送でも重複保存を防げる境界を設ける必要がある。
対策はキーの有効範囲・保持期間と、保存との原子性まで決める。保存成功後の応答喪失と同時再送を再現し、注文が一件で同じ結果を返すことを確認する。

### 判断に必要な未確認事項

- **説明不足:** 「閲覧」で注文の所有者をどこで確認するか不明。認証だけでは他者の注文を読めないと判断できない。権限の要求と共通処理を確認し、権限外の注文を指定した場合の応答を確かめる。現時点では情報漏えいがあると断定しない。
- **検証未実施:** 要求 R2 の負荷条件での性能は未計測。設計の見積もりと計測条件を確認し、R2 の条件で負荷試験を行う必要がある。遅いという指摘や合格判定にはしない。

### 確認範囲と残るリスク

**検証方法：机上での追跡。** 提示された設計と要求を読み、正常な注文作成と応答喪失後の再送を追跡した。シミュレーション・モデル検査・実装のテストは実施していない。
再送経路は R1 違反として設計修正が必要。閲覧権限と性能は判断に必要な根拠が不足しており、確認後に再評価する。

## 問題が見つからない場合

例えば、同じキーでの再送と保存を一つの原子的な処理で扱う設計について、確認した経路に矛盾がなければその旨を返す。
「指摘なし」は全経路の正しさを意味しない。確認した条件と未実施の検証だけを残し、指摘や追加機構を無理に作らない。
