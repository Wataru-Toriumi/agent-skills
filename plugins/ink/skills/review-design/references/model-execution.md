# モデルを実行して設計を確かめる

競合・再送・障害・状態遷移の組み合わせが設計の判断を左右する場合に読む。
検証したい性質を先に決め、その性質を保った小さなモデルで探索する。

## 方法を選ぶ

| 方法 | 適用する場面 | 結果が示す範囲 |
| --- | --- | --- |
| 机上での追跡 | 利用側のコードや操作列で設計の契約・経路を確認できる | 明示して追った経路についての判断。ツールでの実行ではない |
| シミュレーション実行 | 多数の操作順序や障害の組み合わせから反例を探したい | 実行した試行・経路での結果。反例がないことは網羅を意味しない |
| モデル検査 | 定義した状態空間や深さの範囲で性質を機械的に検査したい | モデル・仮定・設定した範囲に限定した結果。タイムアウトや中断は完了ではない |
| 実装のモデルベーステスト | 動く実装・試作品があり、仕様との一致を確かめたい | 実装に適用した操作列と比較した性質についての結果 |

[Quint](https://quint.sh/docs/what-does-quint-do) は状態モデルのシミュレーションとモデル検査に使える。
[TLA+ / PlusCal と TLC](https://docs.tlapl.us/) も設計モデルの検査に使える。
Quint は実行方式やバックエンドによって探索範囲が異なるため、[モデル検査の説明](https://quint.sh/docs/model-checkers) と利用するバージョンの公式手順を確認する。
TypeScript の実装・試作品を検証する場合は、既存のテスト環境に合えば [fast-check のモデルベーステスト](https://fast-check.dev/docs/advanced/model-based-testing/) などを使う。
実装をそのまま期待結果のモデルへ写すと、同じ誤りを見逃すため、要求から比較する性質を定める。

## モデルを設計に対応付ける

- 状態変数、初期状態、操作、失敗・再送、操作を分割する境界を定め、設計の節や要求 ID と対応付ける。
- 常に守る条件と、最終的に完了してほしい条件を区別する。後者は復旧や公平性などの前提も明記し、単に不変条件を調べただけで確認済みにしない。
- 独立した書き込みや外部呼び出しを、根拠なく一つの原子的な操作にまとめない。調べたい競合や障害を抽象化で消さない。
- プロセス数、入力値、キュー長、探索深さなどを絞り、省略した挙動を示す。モデル中の仮定と実装上の保証を区別する。

## 実行し、根拠を残す

1. 利用可能なツールとバージョンを確認する。一時的な隔離場所で、検証対象と無関係な外部サービスを呼ばないモデルを使う。ホスト固有の機能を必須にしない。
2. 時間・試行数・探索範囲の上限を決めて実行する。反例を得るか、設定した探索を終えるか、上限へ達した時点で結果を整理する。未導入などで実行できなければ、机上の評価と実行に必要な条件を返す。
3. 反例が出たら、入力・状態・操作列を元の設計へ戻して確認する。モデル化の誤りや未合意の仮定が原因なら、設計の欠陥と断定しない。対策案を試す場合は元のモデルと区別し、合格させるために要求を弱めない。
4. コマンド、ツールのバージョン、モデル・設定、シード（該当する場合）、探索の上限と実績、完了・中断、反例を再現できる形で残す。ファイルを残す依頼がなければ、会話内の必要なモデル断片や操作列で説明する。

モデルで問題が見つからなくても、実装との一致、実環境の性能、モデル化しなかった障害まで確認済みとはしない。
