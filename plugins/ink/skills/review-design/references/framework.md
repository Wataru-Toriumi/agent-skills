# ATAM・ARID を設計レビューに使う

[ATAM](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/) は、アーキテクチャの品質に関する設計判断とリスク・トレードオフを評価する手法。

[ARID](https://www.sei.cmu.edu/library/active-reviews-for-intermediate-design-arid/) は、設計を利用する開発者がシナリオを選び、そのサービスを使うコードを組み立てて適合性を確かめる手法。

両者の考え方を個別の設計レビューに応用する。正式な評価や正しさの証明ではなく、全品質属性の評価を必須にしない。
エージェントによる追跡を、関係者の評価や合意の代わりにはしない。

## 要求からシナリオを選ぶ

要求への影響と、成立が不確かな設計判断を手掛かりに優先する。発生確率を根拠なく数値化しない。
既知の負荷や運用条件があれば使い、未知なら条件付きで評価する。

| 設計に関わる論点 | 選ぶシナリオの例 | 確認すること |
| --- | --- | --- |
| 整合性・権限 | 同時更新、重複配送、権限を失った利用者からの操作 | 守るべき条件、判定と更新の境界、状態の所有先 |
| 可用性・復旧 | 依存先の停止、保存直後のプロセス停止、復旧後の再処理 | 影響範囲、失敗の検知、再試行や復旧で失われるもの |
| 性能・容量 | 想定ピーク、遅い依存先、処理待ちの増加 | ボトルネック、上限、待ちや拒否の挙動、計測条件 |
| 変更容易性・移行 | 外部 API の変更、新旧バージョンの共存、移行途中の失敗 | 変更が波及する範囲、互換性、適用順序、戻せるデータ |

網羅用のチェックリストではない。対象が単一プロセスの小さな処理なら、その責務や失敗境界を追えばよい。

## 設計を使って確かめる

選んだシナリオを、公開された操作・入力・返り値・エラーだけで実現してみる。
例えば注文の再送なら、同じ操作を識別する値をどこで生成し、呼び出し側が何を保持し、再送の結果をどう判別するかまで書く。
内部の重複防止機構が説明されていても、利用側から必要な情報を渡せなければシナリオは成立しない。

机上では、各操作の前後の状態と外部への副作用を表や短いトレースに残す。
成功する経路だけでなく、重要な境界で停止・再送・競合を挟む。未知の挙動は未決として扱い、想定した擬似コードを実行済みと報告しない。
経路の組み合わせを手で追い切れない箇所は [モデル実行](model-execution.md) へ進む。全シナリオへのツール導入を必須にはしない。

## 合格条件と判断のつながり

シナリオは「状況・起点・対象・期待する応答・合格条件」で記す。
例えば、応答を受信できなかったクライアントが同じ注文を再送する場合、要求が重複防止なら、保存される注文が一つで同じ結果を返せるかを追う。
性能の基準が未決なら「何ミリ秒以下」と創作せず、対象操作・負荷条件・計測方法と、合意が必要な基準を示す。

判断を左右する条件も残す。重複防止キーの保持期間より後の再送を認めるなら、保証できる範囲が変わる。
保持期間を延ばすと重複防止の範囲は広がるが、保存容量や削除運用に影響する。
こうした一つの判断が複数の品質へ与える影響を、要求と制約に照らして比較する。常に冗長化や新しいサービスを追加する結論にしない。

評価結果は「シナリオ → 設計上の経路 → 要求への影響 → 根拠または未確認事項 → 検証方法」で追えるようにする。
