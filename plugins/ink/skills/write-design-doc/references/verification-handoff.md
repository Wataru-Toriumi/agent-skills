# 要求・設計を probe の検証へ渡す

要求や設計の合否を何で確かめるか具体化する場合に使う。既存の検証計画で足りる部分は再作成しない。

| 必要なこと | 利用可能なら使う probe のスキル |
| --- | --- |
| リスクに応じたテストの種類・範囲・優先度を決める | `plan-tests` |
| 方針から前提・操作・期待結果のあるケースを作る | `design-tests` |
| 既存の方針やケースの妥当性を確認する | `review-test-cases` |
| 状態遷移・関係・契約などの性質を形式化して確かめる | `verify-formally` |

1. 要求 ID・設計の節と版、対象の利用経路、受け入れ条件、設計上のリスク・失敗経路、守るべき条件を渡す。現行実装と提案中の設計、確定した制約と仮定・未決事項を区別する。
2. 既存のテストや計画、対象外、利用可能な環境と、今回の到達点を添える。方針の具体化、ケース作成、レビュー、形式検証の選定・実行を分け、必要な工程だけ進める。形式検証では必要な保証範囲と実行上限も渡す。
3. probe から要求・リスクと検証方法の対応、合否基準、必要な環境、未確認範囲を受け取る。実行した場合だけ結果・対象の版・証跡・保証範囲を付け、計画やケースの完成を検証成功と扱わない。
4. 元の要求・設計と照合して検証計画へ反映する。期待結果を左右する未決事項は ink 側で判断し、probe に仕様を補わせない。影響しない経路の方針やケースは進めてよい。

設計段階では実装や差分がなくても進める。性能目標などが未定なら合否基準を未決とし、一般的な数値を補わない。
文書作成だけの依頼では、必要な検証計画までを扱い、製品コード・恒久的なモデル・実環境の変更へ広げない。設計レビューで必要な一時モデルの検証は、元のレビュー手順の範囲に従う。
probe が利用できなければ、要求・リスク・確認方法・未決事項を自分で整理する。新しい文書やプラグインの導入を前提にしない。
