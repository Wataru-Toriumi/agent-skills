# 要求から設計・検証へつなぐ例

以下は架空の入力に対する草案。構成・パス・仕様を実案件の事実として流用しない。

## 入力

- R-001: 申請者が自分の申請の進捗を確認できる。
- R-002: 申請者は他人の申請を閲覧できない。
- 現状資料で、Web アプリ・API・申請データストアがあり、API が認証を担うことを確認できたとする。
- 通知と承認者向け機能は対象外。権限を確認できない場合に許可しないことは確定した制約。
- エラーの表示方法は未合意。性能目標は提示されていない。

## 出力例

### 目的

R-001・R-002 を既存の申請照会に追加する。通知と承認者向け機能は対象外。
既存構成は入力の現状資料を参照する。

### 提案する設計

API の申請照会で、認証済みの申請者と申請の所有者を照合してから進捗を返す。
既存 API の認証と申請データを利用できるため、照会専用のサービスは新設しない。
照会のたびに所有者確認が必要になる負担は受け入れる。画面だけの制限では API への直接アクセスを防げないため、API で判定する。

構成は Web アプリ → API → 申請データストア。API が閲覧可否を判定し、データストアは申請の所有者と進捗を保持する。

1. 認証済みの申請者が Web アプリから申請を照会する。
2. API が申請を取得し、所有者を認証情報と照合する。画面から渡された申請者情報をそのまま信用しない。
3. 自分の申請なら進捗を返す。他人の申請なら申請内容を返さない。
4. データ取得に失敗し、所有者を確認できない場合も内容を返さない。進捗を推測して表示しない。

未決: 存在しない申請・権限不足・取得失敗を利用者にどう伝えるかは、情報公開方針と既存のエラー契約を確認して決める。本文では具体的な HTTP ステータスや文言を確定しない。
データ形式の変更は提案していないため、データ移行の節は設けない。

### 検証計画

| 要求・リスク | 対応する設計 | 検証方法・合格条件 |
| --- | --- | --- |
| R-001 | API の所有者照合と進捗返却 | 自分の承認待ち申請を照会し、承認待ちと確認できること。 |
| R-002 | API 側の閲覧可否判定 | 他人の申請を API へ直接要求しても申請内容が返らないこと。 |
| 取得失敗で権限を確認できない | 失敗時に内容を返さない処理 | データ取得を失敗させ、申請内容が返らず、画面にも推測した進捗が表示されないこと。エラー表示の合格条件は方針確定後に追加する。 |

以上は検証計画であり、実施結果ではない。

## この例で省いているもの

構成が単純なため図は作らず、正常系と権限・取得失敗の経路を短い手順で表している。
性能要件が提示されていないため、SLO や数値目標を追加していない。
新しい外部連携やデータ移行がある案件では、契約・整合性・移行途中の失敗など、その変更に関係する説明を足す。
