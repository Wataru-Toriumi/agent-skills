# フレームワークを短い Design Doc に使う

設計に必要な観点と、説明の粒度を選ぶための資料。フレームワークの項目を埋めることを目的にしない。

## arc42 の観点を使う

[arc42](https://arc42.org/overview/) はソフトウェアアーキテクチャを説明するための構成を提供する。
このスキルでは、その観点を次のように基本3節へまとめる。arc42 の全12節への準拠を意味しない。

| 基本の節 | 確認すること |
| --- | --- |
| 目的 | 実現する要求と品質上の目標、制約、システム化の範囲 |
| 提案する設計 | 外部との境界、構成と責務、実行時の振る舞い、選択理由と不利益 |
| 検証計画 | 要求と品質条件を満たすか、設計上のリスクをどう確認するか |

配置・運用の変更や移行がある場合など、判断に必要な内容は「提案する設計」に加える。
長い背景や個別判断の履歴は PRD・ADR を参照し、転記しない。

構成要素の列挙だけでは、動作する設計か判断できない。[実行時の観点](https://docs.arc42.org/section-6/)で、重要な要求と失敗経路をその構成上で追う。
[品質シナリオ](https://docs.arc42.org/section-10/)を参考に、品質上の要求を状況・起点・応答と確認可能な基準に落とす。例えば「高速」とだけ書かず、どの操作をどの条件で計測するか、合格基準は確定しているかを示す。

## C4 で構成の粒度を選ぶ

[C4 model](https://c4model.com/diagrams) は、構成を異なる粒度で説明するためのモデル。
今回の論点を伝えられる粒度だけを選ぶ。

| 論点 | 粒度・表現 |
| --- | --- |
| 誰が使い、何と連携するシステムか | システムコンテキスト |
| アプリケーションやデータストアにどう責務を分けるか | コンテナ |
| アプリケーション内部のどの部分が責務を担うか | 必要な範囲のコンポーネント |
| どんな順序で連携し、失敗時に何が返るか | 構成と名前を揃えた手順・シーケンス図 |
| 実行環境やノードにどう配置するか | 配置の説明・デプロイメント図 |

[C4 のコンテナ](https://c4model.com/diagrams/container)はアプリケーションやデータストアを指し、Docker コンテナと同義ではない。
小さな処理変更なら既存モジュールの説明で足りる。図やフレームワークに合わせて構成を大きくしない。
既存の図があれば差分を中心に更新し、C4 の厳密な表記を使っていない図を C4 準拠と呼ばない。

## PRD・ADR との接続

- PRD の要求と受け入れ条件を、設計の責務・処理・検証へつなぐ。複数アクターの許可範囲や要求の衝突も引き継ぐ。
- 要求が未決なら、影響範囲と選択肢を示し、都合のよい要求に置き換えない。
- 技術判断の理由を短く示し、独立して残す価値のある判断は ADR 化の候補として伝える。文書作成の依頼だけで別の成果物を増やさない。
