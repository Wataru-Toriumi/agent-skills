# Design Doc を作成・更新する

要求をどう実現するかを、実装者とレビュアーが判断できる粒度で説明する。
arc42 の要求・境界・構造・実行時の振る舞い・設計判断・品質の観点を使い、今回の変更に必要な内容を整理する。
図が有用なら C4 model を参考に粒度を選ぶ。これは両者の考え方を短い Design Doc に応用する手順であり、全項目や全種類の図を必須にするものではない。既存のフレームワーク・書式があれば優先する。

## 文脈と保存先

- 入力の要求、関連する仕様・設計・コードを確認し、現行の仕組みと今回の変更点を把握する。PRD がなくても、与えられた要求から進めてよい。
- 文書の言語、書式、保存先はユーザーの指定とリポジトリの慣例に合わせる。新規作成で慣例がなければ `docs/design/<topic>.md` を使う。チャット上の草案を求められた場合はファイルを作らない。
- 更新では既存の設計判断と理由を読み、今回変える部分と関連する節を整合させる。変更対象外の判断を理由なく置き換えない。

## 設計の前提を揃える

- 対象の要求と受け入れ条件、関係するアクター・外部システム、対象外、確定した制約を拾う。PRD の要求 ID と出所を引き継ぐ。PRD がない場合も入力から要約し、PRD の作成を前提条件にしない。
- 現状の責務・データ・依存先をコードや資料で確認し、現状と今回の提案を区別する。アクセスできない実装や未計測の性能は、確認済みとして書かない。
- 要求の衝突や未決の権限方針が設計を変える場合は、影響する部分を明示して確認する。合意を代わりに決めず、残りの設計は進め、必要なら条件付きの案を示す。明らかな情報を聞き直さない。

## 設計を組み立てる

1. **方針と境界:** 何をどう変えるかを先に示し、実現する要求、対象外、制約を短く結び付ける。利用者や外部システムと今回のシステムの境界、変更する範囲を明確にする。
2. **構成と責務:** 主要な要素の責務、依存関係、データの所有先を示す。既存の要素と新設・変更する要素を区別し、各主要要求をどこで実現するか対応付ける。小さな変更では関数やモジュールの説明だけでよく、新しいサービスを増やさない。
3. **実行時の流れ:** 代表的な操作やイベントについて、入力から結果までを構成要素に沿って説明する。関係する権限判定、保存・状態遷移、外部呼び出しと、設計を左右する失敗経路を含める。正常系だけで成立したことにしない。
4. **選択理由:** 要求・制約・品質上の基準に照らして方針を説明し、受け入れる不利益を記す。選択が分かれる場合は現状維持を含む現実的な代替案と比較する。検討履歴や採用の合意は捏造せず、既存 ADR に理由があればリンクする。
5. **検証:** 各主要要求と設計上のリスクに、対応する設計箇所・検証方法・合格条件を付ける。PRD の受け入れ条件を弱めず、技術的な成立を何で確認するか具体化する。未実施の検証を成功済みと書かない。

品質上の要求が設計を左右する場合は、「状況・起点となる出来事・期待する応答・測定条件と合格基準」で具体化する。数値が未定なら未決と確認方法を示し、一般的な SLO や負荷条件で埋めない。
構成、実行時の流れ、検証で同じ要素名と要求 ID を使い、関係がつながるかを往復して確認する。

新規文書は [Design Doc テンプレート](assets/design-doc-template.md) の「目的・提案する設計・検証計画」を基本とする。既存書式がある場合はそちらを優先する。

## 図と説明の粒度を選ぶ

- Mermaid を使う場合、利用可能なら `sketch` プラグインの `draw-mermaid` スキルを適用する。図の目的・読者・粒度・要素と関係・掲載先を渡し、返された図と本文の設計を照合する。利用できなくても作成を続け、描画を確認できていなければその旨を伝える。
- 関係者や外部との境界が論点なら C4 のシステムコンテキスト、アプリケーション・データストア間の責務が論点ならコンテナの粒度を使う。ここでのコンテナは Docker に限定しない。
- 内部の責務分担が論点のときだけコンポーネントへ掘り下げる。同じ図にシステム全体と細かな関数を混在させない。変更の判断に役立たない粒度や図は追加しない。
- 処理順序・失敗時の応答が論点なら番号付きの手順やシーケンス図、環境への配置が論点ならデプロイメント図を選ぶ。構成図だけで処理順序や配置まで説明したことにしない。
- Mermaid など利用先で扱える形式を使い、要素の役割、接続の意味、現状か提案かを示す。図は必須ではない。適用する観点や粒度に迷う場合は [フレームワークの使い方](references/framework.md)、文書への落とし込みは [整理例](references/design-example.md) を参照する。

## 説明を追加する条件

- 呼び出し側との契約や保存形式が変わる場合は、インターフェースと互換性を具体化する。
- 失敗時の動作、権限・データの扱い、性能が設計判断に影響する場合は、その挙動や制約を記す。存在しない負荷要件や運用基準を作らない。
- データ移行や段階的な展開が必要なら、新旧の共存、適用順序、途中失敗の扱い、切り戻せる範囲を記す。書き換えたデータも元に戻せるとは仮定しない。
- 実装・レビューを妨げる未決事項があれば、影響と確認方法を示す。説明が短ければ基本の節に含め、長くなる場合に節を追加する。

## 仕上げ

- 判断に必要な最小限の文章にする。PRD の背景や ADR の理由は転記せずリンクし、一般論や作業の時系列を省く。空の節や無関係な項目は作らない。文字数を減らすために重要な設計・リスク・検証条件を落とさない。
- 主要要求に対して設計と検証方法が揃い、要求にない機能を追加していないか確認する。図・本文・検証の要素と権限条件が一致し、境界での失敗や移行に矛盾がないか確認する。
- 確定事項、提案、仮定、未決事項を区別する。個別の判断が ADR として記録済みなら参照し、内容を矛盾させない。
- コード断片はインターフェースや処理の理解に必要なものに絞る。文書作成の依頼だけで、実装や外部サービスの変更まで進めない。
- 作成・更新した文書の場所、設計の要点、レビューで判断してほしい論点を短く伝える。
