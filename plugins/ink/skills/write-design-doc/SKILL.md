# Design Doc を作成・更新する

要求をどう実現するかを、実装者とレビュアーが判断できる粒度で説明する。

## 文脈と保存先

- 入力の要求、関連する仕様・設計・コードを確認し、現行の仕組みと今回の変更点を把握する。PRD がなくても、与えられた要求から進めてよい。
- 文書の言語、書式、保存先はユーザーの指定とリポジトリの慣例に合わせる。新規作成で慣例がなければ `docs/design/<topic>.md` を使う。チャット上の草案を求められた場合はファイルを作らない。
- 更新では既存の設計判断と理由を読み、今回変える部分と関連する節を整合させる。変更対象外の判断を理由なく置き換えない。

## 設計を組み立てる

1. 目的、要求、対象外、既知の制約を短く整理する。要求自体に矛盾があれば示し、実現方法の提案と区別する。
2. 現状と提案を分けて記述する。現状の説明には、確認したファイルパスや既存資料を添える。アクセスできないコードの構成は仮定として扱う。
3. 中核となる構成と、要求を満たす処理・データの流れを説明する。責務、境界、主要なインターフェースを明確にし、関係が伝わりやすくなる場合は Mermaid などで図示する。
4. 設計上の判断が必要な箇所について、現状維持を含む現実的な代替案とトレードオフを記す。採用が確認できない案は提案として示し、検討履歴を捏造しない。
5. 変更に関係する失敗時の挙動、互換性、権限・データの扱い、性能上の制約を掘り下げる。存在しない負荷要件や運用基準を作らず、無関係な項目は増やさない。
6. 移行が必要なら展開順序と元に戻せる範囲を整理する。検証では、何をどの方法で確かめるかを要求と対応付ける。未実施のテストや性能測定を実施済みと書かない。

新規文書の構成には [Design Doc テンプレート](assets/design-doc-template.md) を使える。変更の大きさに合わせて節を選び、既存書式がある場合はそちらを優先する。

## 仕上げ

- 主要要求に対して設計と検証方法が揃っているか、境界での失敗や移行の矛盾がないか確認する。
- 確定事項、提案、仮定、未決事項を区別する。個別の判断が ADR として記録済みなら参照し、内容を矛盾させない。
- コード断片はインターフェースや処理の理解に必要なものに絞る。文書作成の依頼だけで、実装や外部サービスの変更まで進めない。
- 作成・更新した文書の場所、設計の要点、レビューで判断してほしい論点を短く伝える。
