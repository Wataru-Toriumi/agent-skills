# テスト方針を決める

変更のリスクに応じて検証範囲を選ぶ。小さな変更は会話内の数行で済ませる。

## 変更と影響を捉える

- 要求・受け入れ条件・差分・既存テストから、変更前後の振る舞いと影響する利用経路を整理する。要求 ID や資料の節を引き継ぐ。
- 主要な正常系と、権限・データ・外部接続・状態変化などの関連リスクを選ぶ。コードや既存テストだけを期待動作の根拠にしない。
- 対象環境、実施時間、利用できるデータや接続先を確認する。不明な要求や性能目標は推測で埋めず、未決事項に分ける。

## 必要なテストを選ぶ

[テストの分類と選び方](references/test-types.md) を使い、範囲・品質・目的・設計技法・実施方法を分ける。
すべての分類を埋めず、検出したい失敗に必要なものを選ぶ。

- 失敗を検出できる最小の範囲を選び、接続や業務全体の検証を補う。実接続と代替実装を区別し、選んだ方法で分からない点を残す。
- 既存テストの再利用・修正・追加を分ける。存在だけで成功済みとせず、不具合修正では修正確認と回帰確認をそれぞれ選ぶ。
- 利用者への影響、発生可能性の根拠、変更の波及範囲で優先度を決める。重大な失敗は、低頻度や検証の難しさだけで後回しにしない。
- 対象外・時間不足・環境不足で省く範囲と、残るリスクを示す。「成立しない」として除外するなら、到達を防ぐ制約と適用範囲を確認する。

## 方針を返す

既存の書式を優先し、検証対象ごとに次をまとめる。共通の前提は一度だけ書く。

- 要求・変更と、検出したい失敗。
- テストの種類・範囲・選定理由・優先度。基準がなければ「リリース前に必須」などの実施時期で示す。
- 実施方法、必要な環境、完了の判断基準、未決事項と残るリスク。

ケース作成も依頼された場合は、この方針を [design-tests](../design-tests/SKILL.md) に引き継ぐ。
レビューには、方針・ケースと元の要求・差分を渡す。
既定の出力先は会話。方針の依頼だけでケース作成・実装・実環境での実行・外部への登録まで進めない。
