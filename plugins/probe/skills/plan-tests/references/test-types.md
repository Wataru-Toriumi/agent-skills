# テストの分類と選び方

## 分類の軸を分ける

同じケースを次の軸で分類する。「結合」「E2E」などは既存の呼び方に合わせ、実際につなぐ対象を確認する。

| 軸 | 整理する内容 | 例 |
| --- | --- | --- |
| 範囲・レベル | どの単位や接続を確かめるか | 単体、コンポーネント結合、システム、システム結合、受け入れ |
| 品質 | 何を満たすか | 機能、性能、セキュリティ、使いやすさ、アクセシビリティ、信頼性、互換性 |
| 目的 | 今回なぜ実施するか | 新機能の確認、不具合の修正確認、回帰確認、スモーク |
| 設計技法 | どうケースを導くか | 仕様に基づく境界値、構造に基づく分岐、経験に基づく探索 |
| 実施方法 | どう確かめるか | 手動・自動。対象を実行する動的テスト、実行せず調べるレビュー・静的解析 |

例えば「API と DB をつないで、他人の予約を変更できないことを自動で回帰確認する」は、結合・機能／セキュリティ・回帰・自動の組み合わせになる。
探索的テストは手動全般の別名ではなく、学習・設計・実行を往復する進め方として扱う。

## 範囲を選ぶ

| レベル | 選ぶ場面 | これだけでは分からないこと |
| --- | --- | --- |
| 単体 | 計算・判定などを独立して確かめる | 実際の接続先との整合 |
| コンポーネント結合 | 内部モジュールやデータアクセスの接続を確かめる | 製品全体の利用経路 |
| システム | 製品全体の振る舞いや品質を確かめる | 代替した外部サービスの実際の挙動 |
| システム結合 | 外部 API や別システムとの接続を確かめる | 利用者が業務を完遂できるか |
| 受け入れ | 利用者・運用者の要求を満たし、導入できるか判断する | 内部の全分岐や全障害経路 |

E2E は、開始操作から最終結果まで通す経路を明記する。UI 操作の有無や「受け入れ」と同義にはしない。
契約テストは API・イベントの約束を提供側と利用側で確かめるために選び、実通信や業務全体の検証とは分ける。

## 品質に合う条件を選ぶ

| 確認する品質 | 選ぶ場面と必要な条件 |
| --- | --- |
| 機能 | 業務ルール・入力・状態を変えるとき。受け入れ条件と観測可能な期待結果を置く |
| 性能 | 件数・同時利用・処理量が問題になるとき。通常負荷、限界、継続運転のどれを調べるか選び、負荷条件と応答時間・エラー率などの基準を置く |
| セキュリティ | 権限・外部入力・秘密情報を扱うとき。アクター、資産、侵入経路を特定する |
| 使いやすさ・アクセシビリティ | 操作や情報の理解に影響するとき。利用者のタスク、操作手段、支援技術などを選ぶ。自動検査だけで利用可能と断定しない |
| 信頼性・回復 | 障害、再送、復旧に影響するとき。障害の注入箇所、保持すべきデータ、復旧後の状態を決める |
| 互換性 | API・ブラウザー・保存形式などを変えるとき。対応する版と新旧の組み合わせを明示する |

非機能の確認も必要なレベルから始め、実環境に近い条件が必要な測定を補う。

## 目的と実施方法を決める

- **修正確認:** 元の不具合が再現する条件で、修正後に解消したか確かめる。
- **回帰確認:** 変更の影響範囲から、既存機能への副作用を確かめる。修正確認だけで代用しない。
- **スモーク:** 配備後などに、起動と主要経路を短時間で確認する。網羅的な回帰確認の代わりにはしない。

反復し、結果を機械的に判定できる確認は自動化の候補にする。
使いやすさの評価や未知の経路の探索では人の判断を使い、データ準備・記録などをツールで補えるか検討する。
静的な確認で見つけた問題と、実行して観測した結果は区別する。

## 選定例

| 変更 | 選ぶ確認 | 残る限界 |
| --- | --- | --- |
| 料金の丸め方を修正 | 単体で境界値と修正確認。請求への反映を結合で回帰確認 | これだけでは大量請求時の性能は分からない |
| 外部決済 API の版を更新 | 契約とシステム結合で互換性・失敗応答を確認。主要な決済経路を E2E で回帰確認 | サンドボックスでは本番の負荷や障害特性を再現できない場合がある |
| 予約フォームを変更 | 機能の回帰確認と、利用者タスクに沿った受け入れ・アクセシビリティの確認 | 画面の成功だけでは API への直接入力に対する防御は分からない |
