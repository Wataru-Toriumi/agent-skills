# 検証から要求・設計・実装へ戻す

期待結果の未決、ケースの不備、反例や不一致を見つけたとき、次に判断・修正する対象を選ぶ。

| 確認した内容 | 次の工程 |
| --- | --- |
| 期待動作が未決、要求が衝突する | 利用可能な ink の `clarify-requirements`・`review-requirements` で、決める問いと根拠を整理する |
| 要求は明確だが、設計に違反経路がある | 利用可能な ink の `review-design` で評価する。設計修正も依頼されていれば `write-design-doc` へ渡す |
| 実際のコードで要求との不一致が成立する | 修正も依頼されていれば、利用可能な forge の `implement-work-item` に渡す |
| テストの期待値・準備・環境、モデル・仮定が対象と合わない | まずその不備を切り分け、依頼範囲で方針・ケース・モデルを見直す。製品の欠陥と断定しない |
| タイムアウト・ツール不足などで結論が出ない | 未完了の性質と必要な環境・次の検証を返す。合否やコード修正の根拠にしない |

1. 要求・設計・コード・ケース・モデルの対象版を揃える。元の要求 ID、期待結果と根拠、観測結果、再現条件・操作列、証跡、影響を渡す。机上の指摘・実行結果・仮定を分ける。
2. 形式検証では、仮定・探索範囲・省略した挙動と、反例が設計や実装で成立するかを添える。モデルだけの反例を、実装で再現済みとしない。未決の期待動作を probe 側で確定しない。
3. 確認事項と修正対象を分け、依頼の到達点を保って引き継ぐ。レビュー・検証だけなら指摘と次の対応を返し、要求・設計・製品コードの変更へ広げない。修正まで依頼済みなら同じ許可を聞き直さず進める。
4. 修正後は変更した版と対象を受け取り、影響する条件・ケース・モデルの対応を再確認する。要求が変わった場合は変更理由と合意を確認し、失敗を消すためだけに期待結果を弱めない。旧版の成功を新しい版の証跡に流用しない。

反例を回帰ケースにする場合は、元の性質、成立する前提・操作列・観測できる期待結果を `design-tests` へ渡す。実装で成立しないモデル上の経路を、そのまま実装テストにしない。
連携先が未導入でも、同じ情報と必要な判断・修正・再検証を返して依頼範囲を進める。同じ未決事項をスキル間で渡し続けず、判断に必要な情報と確認先を残す。
