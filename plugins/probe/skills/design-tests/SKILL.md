# テストを設計する

要求を満たすか判断できるケースを設計し、重要な失敗を優先して検出する。

## 方針と期待動作を揃える

- 方針の対象・種類・優先度・対象外を、要求・差分と照合する。方針がなければ、主要リスクと検証範囲を短く置いて進める。種類の選定が必要なら [plan-tests](../plan-tests/SKILL.md) を参照する。
- 利用者・権限・入力・状態と期待結果を拾う。コードや既存テストだけを正解の根拠にしない。
- 既存の要求 ID や資料の節を引き継ぐ。曖昧・矛盾する条件は確認事項とし、期待結果や性能目標を推測で埋めない。

## ケースの成立条件を整理する

対象の環境と入口を特定し、入力・状態・操作の組み合わせを分類する。

| 区分 | 判断の根拠 | 扱い |
| --- | --- | --- |
| 起こりうる | 成立する入力や、操作・障害の経路を示せる | テスト候補にする |
| 成立しない | 条件が矛盾する、または確認済みの制約で到達できない | 除外し、根拠と適用範囲を残す |
| 判断できない | 到達経路や制約の有効性を確認できない | 確認事項に残し、必要な資料・検証を示す |

禁止された操作でも、要求が届くなら拒否を検証する。
UI の制限・型定義・発生実績のなさだけで除外せず、API・保存済みデータ・再試行・競合などの関連経路を確かめる。
到達を防ぐ制約自体の検証は残し、前提が変われば分類を見直す。
具体例は [成立条件の判断例](references/test-design.md#成立条件の判断例) を参照する。

## 観点をケースにする

技法の選択やケースの粒度は [テスト設計の判断例](references/test-design.md) を参考にする。

- 各ケースに、短いタイトル、要求・リスク、優先度、前提とデータ、操作、期待結果を含める。共通の前提はまとめ、独立した失敗は分ける。
- 既存ケースの再利用・修正・追加を分ける。方針の優先度を引き継ぎ、具体化で新たなリスクが見つかれば方針への影響を示す。
- 表示・応答・保存状態・副作用など、合否を判定する観測方法を書く。拒否時は、不要な更新や送信が起きないことも確かめる。
- 再現に必要な環境・ユーザー・データの準備と後片付けを示す。内部名や処理順は、その契約を検証するときだけ書く。
- 手動で探索するなら目的と終了条件を置く。

## 抜けと重複を確認して返す

要求・主要リスクとケースを照合し、抜けと根拠のないケースを確認する。
同じ失敗の重複は統合し、権限・境界・状態が異なる検証は残す。
期待動作が未決なら合否判定待ちとし、設計済みと実施済みを区別する。
別途レビューを依頼された場合は [review-test-cases](../review-test-cases/SKILL.md) を使い、ケースと方針を元の要求・差分から評価する。

既存の書式を優先し、次をまとめる。

- 対象と前提、優先するリスク。
- 要求・リスクと対応づけたテストケース、実施方法。
- 除外した組み合わせと根拠、未決事項、対象外・未カバーの範囲と残るリスク。

既定の出力先は会話。テスト実装・実環境での実行・外部への登録は依頼がある場合に行う。
実行時は対象環境と操作範囲を確かめ、結果と証跡をケースに対応づける。
