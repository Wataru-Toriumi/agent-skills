# テスト設計の判断例

## 条件に合う技法を選ぶ

| 条件 | 技法 | ケースの選び方 |
| --- | --- | --- |
| 入力範囲や形式で扱いが変わる | 同値分割・境界値 | 同じ扱いの集合から代表を選び、許可範囲の端とその外側を加える。空・未指定は仕様上の扱いが違う場合に分ける |
| 複数の条件で結果が変わる | デシジョンテーブル | 条件と結果を表にし、成立するルールを確かめる。結果を変えない条件はまとめる |
| 状態と操作履歴で結果が変わる | 状態遷移 | 許可・禁止された遷移と、その後の状態を確かめる。再実行や順序が意味を持つなら操作列にする |
| 独立した設定の組み合わせが多い | ペアワイズ | 2条件の組み合わせを効率よく確認する。既知の複数条件にまたがる障害や重大な組み合わせは別に残す |
| 仕様だけでは使いにくさや想定外の経路を拾いにくい | 探索的テスト | 調べるリスク、操作範囲、時間枠、記録する証跡を決める。実施後に観察結果と未探索の範囲を残す |

## 成立条件の判断例

| 候補 | 判断 | 扱い |
| --- | --- | --- |
| 画面では選べない人数を API に送る | 要求が API に届くなら起こりうる | 入力の拒否と保存状態の維持を確かめる |
| 通信断の後、同じ変更要求が再送される | 再送経路があれば、実績がなくても起こりうる | 重複処理や応答の扱いを確認する |
| 同一時点の状態値が「確定」かつ「キャンセル」になる | 単一の値で状態を表すモデルでは矛盾する | 除外する。時点・画面・複製先が異なる状態の食い違いは別に扱う |
| 検証後の処理に範囲外の値が渡る | 全経路で事前検証を保証できれば到達しない | 後段の重複ケースを省き、入口の拒否を検証する。迂回経路が不明なら除外しない |
| 二人の操作が重なる | ロックの有効範囲や対象経路が不明なら判断できない | 「同時操作はない」と仮定せず、競合が成立する条件を確認する |

「成立しない」「対象外」「時間不足で実施しない」は別の理由として記録する。
デシジョンテーブルやペアワイズでも、成立しない組み合わせの制約を反映し、残った条件のカバー範囲を確かめる。

## 予約人数を変更する例

架空の予約機能で、次の要求を合意済みとする。

- R1: 本人が、予約確定状態の人数を1〜6人の整数に変更できる。範囲外・整数以外の人数は拒否する。
- R2: 本人以外、またはキャンセル済みの場合は変更できない。
- R3: 拒否された操作では、保存済みの人数は変わらない。

共通の前提は「現在3人の予約がある」。期待結果は操作の応答と、再取得した予約で確かめる。

| ケース | 根拠・技法 | 条件と操作 | 期待結果 | 優先度と理由 |
| --- | --- | --- | --- | --- |
| 本人が人数を変更できる | R1・同値分割 | 確定状態で4人へ変更 | 成功し、再取得でも4人 | 必須：主要操作 |
| 人数の下限・上限を扱える | R1、R3・境界値 | 本人・確定状態で、各ケースを初期化して0・1・6・7人へ変更 | 1・6人は保存、0・7人は拒否され3人のまま | 必須：範囲の誤りを検出 |
| 整数以外の人数を拒否する | R1、R3・同値分割 | 本人・確定状態で1.5人へ変更 | 拒否され3人のまま | 通常の回帰：入力契約を確認 |
| 他人の予約を変更できない | R2、R3・デシジョンテーブル | 別ユーザーで確定状態の予約を4人へ変更 | 拒否され3人のまま | 必須：権限違反を検出 |
| キャンセル後は変更できない | R2、R3・状態遷移 | 本人が確定状態からキャンセルし、4人へ変更 | 拒否され、キャンセル状態・3人を維持 | 必須：禁止された遷移を検出 |

境界値は入力ごとに独立したケースとして実行する。
本人／他人と確定／キャンセルの組み合わせを補い、他人かつキャンセルの場合も拒否・保存状態の維持を確認する。
空入力や文字列は、入口ごとの入力契約を確認して追加する。

同時更新の採用ルールは未決のため、後勝ちか競合として拒否するかを確認する。
上のケースだけで入力検証や競合を網羅したとは扱わない。
