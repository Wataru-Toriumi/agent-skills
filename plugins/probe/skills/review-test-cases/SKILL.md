# テストケースをレビューする

要求を満たさない実装を、提示された方針とケースで検出できるか評価する。

## 根拠と対象を揃える

- ケース・要求・受け入れ条件・差分・方針の対象版と前提を揃え、既存の ID や節で対応を追う。
- 方針がなくても、要求・差分から主要なリスクを拾ってレビューする。要求が不明なら、確認できる範囲と判断待ちの点を分ける。
- 実装や既存テストとの一致だけで正しいとせず、合意済みの仕様と照合する。

## 方針とケースを別々に評価する

まず要求・差分から方針の抜けを調べ、その後にケースを照合する。
種類の選定に迷う場合は [テストの分類と選び方](../plan-tests/references/test-types.md) を参照する。

| 観点 | 確かめること |
| --- | --- |
| 方針の妥当性 | 主要リスクに必要な種類・範囲が選ばれているか。モックで隠れる境界や、修正確認だけでは拾えない回帰がないか |
| ケースの不足 | 要求・リスクからケースへ対応を追えるか。関連する境界・権限・状態・失敗経路が抜けていないか |
| 成立条件と除外 | 前提と操作が両立するか。除外に根拠があるか。低頻度・UI 制限・未確認を到達不能と扱っていないか |
| 判定できる期待結果 | 仕様に基づく合否と観測方法があるか。拒否時の保存状態や副作用まで確認できるか |
| 再現性 | データ、権限、環境、準備・後片付けが足りるか。別ケースの実行順に意図せず依存していないか |
| 重複と優先度 | 同じ失敗の重複で重要なケースを圧迫していないか。異なる境界や層の検証まで重複として削っていないか |

代表ケースを前提→操作→観測の順にたどり、誤った実装を検出できるか確かめる。
机上の評価と実行結果は区別する。指摘の粒度は [レビュー例](references/review-example.md) を参照する。

## 指摘を返す

指摘は影響順に、対象のケース・方針、発生条件、見逃す問題、要求や差分の根拠、最小限の修正案を示す。
優先度は既存の基準を使い、なければ「実施前に修正」などの対応時期と理由を付ける。

- **方針の不足:** 必要な検証の種類や範囲が選ばれていない。
- **ケースの問題:** 不足・重複・成立しない前提・誤った期待結果など、根拠を示せる問題。
- **確認事項:** 仕様や到達経路が不明で判断できない点。欠陥と断定しない。

該当しない区分と重複指摘は省く。指摘がなくても、確認範囲・未確認事項を返す。
ケース数や書式の好みを理由に指摘せず、ケースの妥当性を実行成功やリリース承認と同一視しない。
既定の出力先は会話。修正・実環境での実行・外部への投稿は依頼がある場合に行う。
